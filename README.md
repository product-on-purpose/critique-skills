# critique-skills

Rubric-cited, machine-parseable critique skills that report measured, evidence-graded findings
against a published standard, instead of freeform opinion.

## The claim

Ask a general-purpose model to critique your work and you get fluent, forgettable commentary. It
changes between runs. It cites no standard. It has no way to be wrong. That gap is not a nitpick:
curated, evidence-graded skills measurably raise what an agent produces (SkillsBench,
[arxiv.org/abs/2602.12670](https://arxiv.org/abs/2602.12670)), and the skill ecosystem those gains
depend on is uneven enough that an unaudited public skill is a documented security and quality
risk ([Snyk ToxicSkills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)).
`critique-skills` answers both problems for one job, critique: every
finding a skill in this library emits cites a permanent criterion ID that traces to a published
external standard, WCAG 2.2, the Toulmin model of argument, Diataxis, NN/g's error-message
guidelines, the Federal Plain Language Guidelines, Nielsen's usability heuristics, never to the
model's own improvised taste.

Findings are not prose you parse by eye. Every one is a structured record: a criterion ID, a lane
(`scripted`, produced by a deterministic script, or `judged`, produced by model reasoning under a
fixed four-pass protocol), a severity on a shared 0-4 scale, a location specific enough to navigate
to unaided, a quoted or measured piece of evidence, the part of the standard that was violated, and
an actionable fix. Every run is wrapped in an envelope that pins the skill version, the contract
version, and the model, and carries a `summary.gate` verdict a CI job can act on directly. See
`docs/reference/critique-contract.md` for the full field contract and `docs/how-to/gate-in-ci.md`
for wiring `--gate` mode into a pipeline.

And the library publishes its own performance rather than asserting it. Every skill runs against a
seeded-defect corpus with known ground truth, five times per artifact per model, on two pinned
model tiers, compared against that same rubric-free generic prompt. The lowest number in the whole
published run set is stated plainly, not buried: `critique-clarity` on the Haiku tier holds a
run-to-run consistency of **0.309**, which is the stretch-gate floor precisely because it is where
the library actually measured. The most instructive number is `critique-accessibility`'s own
history. Version 0.1.0 shipped, then lost to the unrubricked baseline on location-level recall on
both pinned tiers, 0.176 against 0.376 on Haiku and 0.306 against 0.776 on Sonnet, and the root
cause turned out to be a location-*reporting* defect, not a detection one: one helper was printing
a line number where the location grammar required a navigable anchor. Version 0.1.1 fixed exactly
that and nothing else, and recall reads 0.976 on Haiku and 0.965 on Sonnet, beating baseline on
both tiers, on both metrics. Both versions are published side by side in the table above; the
failure was not deleted when the fix arrived. That is this library's best evidence that measurement
catches what intuition misses, and it is why the results table above is the front page rather than
an appendix.

## Install

From the product-on-purpose marketplace, in Claude Code:

```
/plugin marketplace add product-on-purpose/agent-plugins
/plugin install critique-skills@product-on-purpose
```

Cross-agent, via the open [skills CLI](https://github.com/vercel-labs/skills):

```
npx skills add product-on-purpose/critique-skills
```

Clone or download directly:

```
git clone https://github.com/product-on-purpose/critique-skills.git
```

New to this library? `QUICKSTART.md` installs it, runs one critique against a bundled example, and
walks the envelope you get back, start to finish, no branches.

## The six skills

Every skill below is invoked the way Claude Code skills normally are: describe what you want
("review this page for accessibility", "a clarity pass on this memo before it goes out") and the
matching skill triggers on its own description. There is no separate CLI. The table is generated
from `library.json` and each skill's own `SKILL.md` frontmatter; a skill only appears here once its
`library.json` status is `active`, so a skill that is built but held back by its own gate does not
silently show up as shipped.

Regenerate with `node scripts/gen-readme-catalog.mjs`. Check for drift with the same command plus
`--check`.

Where the subagent tool is available, every skill above delegates to the `critique-critic`
subagent (`agents/critique-critic.md`) so critique always runs in a fresh context that has not
seen the artifact being authored (`docs/explanation/methodology.md`, Section 7, "Clean-context
critique"). Nothing here auto-applies a fix: skills report findings, a human disposes of them
(`docs/how-to/dispositions.md`), and critique never edits your artifact on its own behalf.

## Where this stops, and thinking-framework-skills starts

**One test decides it: does the framework evaluate a concrete, already-existing artifact against a
published external standard? Yes, it ships here. No, it belongs in `thinking-framework-skills`.**

`critique-skills` and its sibling [`thinking-framework-skills`](#the-family) sit on the same value
chain, think, make, judge, revise, but on opposite sides of that one hard test
(`docs/explanation/methodology.md`, the Two-Part Gate in Section 2, and "What this library is
not," Section 9). Five worked examples from that gate show exactly where the line falls:

| Candidate | Where it belongs | Why |
|---|---|---|
| SWOT analysis | `thinking-framework-skills` | Evaluates a situation, not an artifact |
| Pre-mortem | `thinking-framework-skills` | Prospective: the thing being assessed does not exist yet |
| Six Thinking Hats | `thinking-framework-skills` | A process protocol, not a standard with criteria |
| First-principles reasoning | `thinking-framework-skills` | A lens applied to problems, not a rubric applied to objects |
| "Is this strategy sound?" | `thinking-framework-skills` | No published rubric for strategic soundness survives citation |

A heuristic evaluation against Nielsen's ten heuristics passes both parts of the gate and ships
here, as `critique-usability`. A pre-mortem on the same launch is thinking, not critique, and
belongs in `thinking-framework-skills`. "Red-team this strategy" only graduates into this library
if it is scored against a published rubric; asked plain, it stays thinking. This library is also
not code review (well served elsewhere, out of scope by choice) and not auto-fix (skills report,
they never edit); both are stated the same way in Section 9.

## The family

`critique-skills` is the third library in the product-on-purpose family, listed on the same
marketplace and built to the same [agent-skills-toolkit](https://github.com/product-on-purpose/agent-skills-toolkit)
Advanced Skill Library Standard (this plugin targets Universal tier at v0.1.0, with the
`critique-critic` subagent already at Convergent):

- [`thinking-framework-skills`](https://github.com/product-on-purpose/thinking-framework-skills) -
  the sibling on the other side of the boundary above: evidence-graded thinking methods applied
  before an artifact exists, not to one that already does.
- [`pm-skills`](https://github.com/product-on-purpose/pm-skills) - product management skills and
  sub-agents across the product lifecycle.
- [`agent-skills-toolkit`](https://github.com/product-on-purpose/agent-skills-toolkit) - the
  Standard and validators every family plugin, including this one, conforms to.

None of the three depend on each other technically. They compose: think with one, build with
whatever you use to build, judge the result with this one.
