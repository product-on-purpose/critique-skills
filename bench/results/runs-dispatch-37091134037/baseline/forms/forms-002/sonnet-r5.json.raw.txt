Location: `<form id="form">` opening tag
Evidence: `<form id="form">` has no `method` or `action` attribute
Problem: Without an explicit method, the form defaults to a GET submission, which would place the password (and account number, membership number, etc.) into the URL — exposed in browser history, server logs, and referrer headers.
Fix: Add `method="post"` (and an appropriate `action`) to the form element.

Location: row-phone, the `<p>` following `#phone-input`
Evidence: `<p>We will text you about delivery updates.</p>`
Problem: This explanatory text sits visually near the phone field but is not programmatically associated with it, so screen reader users tabbing to the input won't hear the disclosure.
Fix: Give the paragraph an `id` and reference it from the input with `aria-describedby`.

Location: row-phone2, `#phone2-input`
Evidence: `type="tel" ... pattern="[0-9]+"`
Problem: Restricting a `tel` field to digits-only rejects legitimate phone formatting such as `+1 555-123-4567`, parentheses, or spaces that `type="tel"` is meant to accommodate.
Fix: Remove the digit-only `pattern` (or relax it to allow `+`, spaces, hyphens, and parentheses).

Location: row-website, `#website-input`
Evidence: `<input id="website-input" name="website" required="" type="text">`
Problem: A required "Company website" field is out of place on a consumer account-signup form (full name, email, home address, phone) and will block individual customers who have no company site; it also uses `type="text"` instead of `type="url"`, losing built-in validation and the URL keyboard on mobile.
Fix: Make the field optional (or remove it if this is a consumer signup), and change its type to `url`.

Location: row-member, `#member-input`
Evidence: `placeholder="Must be 8 digits"` with no `pattern` or `maxlength`
Problem: The 8-digit requirement is only communicated via placeholder text, which disappears once the user starts typing, and nothing actually enforces the 8-digit constraint.
Fix: Add `pattern="[0-9]{8}"` and `maxlength="8"`, and move the format hint into persistent helper text instead of relying solely on the placeholder.

Location: row-member and row-acctnum (`#member-input`, `#acctnum-input`)
Evidence: "Membership number (8 digits)" and "Account number" are both `required` on a form titled "Create your account"
Problem: A brand-new signup form cannot require a pre-existing membership number or account number, since a new customer won't have one yet — this will block legitimate new users from ever completing the form.
Fix: Remove these fields from the signup form, or mark them optional/for-existing-customers-only.

Location: row-postal, `#postal-input`
Evidence: `size="3"` on the postal code input
Problem: A visual width of 3 characters is too narrow for most real postal codes (e.g. US 5/9-digit ZIPs, UK "SW1A 1AA"), making the field look wrong and encouraging truncated-looking entry.
Fix: Increase `size` to at least 8-10 characters, or remove the attribute and size via CSS.

Location: row-shipspeed, `#shipspeed-select` options
Evidence: `<option>Overnight</option> <option>Next-day</option> ... <option>International</option>`
Problem: "Overnight" and "Next-day" describe the same delivery speed and will confuse users about which to pick, and "International" is a destination type, not a shipping speed, mixing incompatible categories in one list.
Fix: Collapse "Overnight"/"Next-day" into a single option, and move "International" to a separate shipping-destination control (or remove it from this list).

Location: row-legalname, `#legalname-input`
Evidence: label "Your name", `name="legal_name"`, `autocomplete="name"` — duplicating row-name's "Full name" (`name="full_name"`, `autocomplete="name"`)
Problem: The form asks for the user's name twice under different labels, which is redundant and may confuse users into thinking the two fields need different values.
Fix: Remove the duplicate field, or clearly differentiate its purpose (e.g. "Legal name, if different from above") and explain why both are needed.

Location: row-org, `#org-input`
Evidence: `style="font-size:13px"` and `required=""`
Problem: The inline 13px font is smaller than the rest of the form's text, hurting readability/accessibility, and a required "Organization name" field is mismatched for what otherwise reads as an individual consumer signup.
Fix: Remove the inline font-size override so it matches other fields, and make organization name optional or remove it if this isn't a business account form.

Location: row-contacttime, `#contacttime-input` and its label
Evidence: `<label ... style="display:inline-block;float:left;width:140px">Preferred contact time</label>` next to a free-text `type="text"` input
Problem: The field gives users no guidance on expected format (e.g. "2-4pm" vs "14:00"), inviting inconsistent, unparseable data, and the label uses an ad hoc inline float/width style instead of the layout approach used elsewhere in the form.
Fix: Replace the free-text input with a constrained control (e.g. a `<select>` of time ranges), and remove the inline float styling in favor of consistent layout/CSS.

Location: `#viewdetails-btn`, between row-contacttime and the dob fieldset
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>`
Problem: This button has no associated handler or visible target in the document and interrupts the form's field flow right before the date-of-birth fieldset, suggesting dead or incomplete functionality.
Fix: Either wire the button to its intended behavior (e.g. expanding a details panel) or remove it from the form.

Location: row-dob, `#dob-year-select`
Evidence: year options run only `<option>1950</option>` … `<option>2009</option>`
Problem: This excludes anyone born before 1950 (older than ~76 in 2026) or after 2009 (younger than ~17 in 2026) from completing signup, which is an arbitrary and overly narrow range for a retail customer base.
Fix: Widen the year range to cover realistic customer ages (e.g. current year minus 100 through current year minus a minimum sign-up age).

Location: row-dob, `#dob-day-select`, `#dob-month-select`, `#dob-year-select`
Evidence: first options are `<option>1</option>`, `<option>January</option>`, `<option>1950</option>` with no "choose a value" placeholder, and all three are `required`
Problem: Because each select is pre-populated with a valid-looking default (Jan 1, 1950), a user who never touches these controls will silently submit that fabricated birthdate, and the `required` attribute won't catch it since a value is already "selected."
Fix: Add a disabled, selected placeholder option (e.g. "Select...") to each select so the required validation actually forces a deliberate choice.
