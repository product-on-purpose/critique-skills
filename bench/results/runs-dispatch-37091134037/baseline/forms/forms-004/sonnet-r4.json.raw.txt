Location: `<head>` section
Evidence: `<meta charset="utf-8">` followed directly by `<title>` with no viewport meta tag
Problem: There is no `<meta name="viewport">` tag, so on mobile devices (which this form clearly targets, given the phone/delivery-text field) the page will render at desktop width and require manual zooming/panning.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the `<head>`.

Location: `row-password` div
Evidence: `<input id="password-input" name="password" type="password" autocomplete="new-password" minlength="8" required="">`
Problem: The password has a minimum-length constraint but no visible instructions telling the user the requirement before they submit and hit a validation error; unlike the phone field, there's no helper text.
Fix: Add helper text under the field (e.g. "At least 8 characters") similar to the note under the phone input.

Location: `row-phone` and `row-phone2` divs
Evidence: both `phone-input` and `phone2-input` use `autocomplete="tel"`
Problem: Using the identical autocomplete token for two different phone fields will cause browsers to autofill the same stored number into both the primary and "secondary" phone fields.
Fix: Differentiate the tokens, e.g. keep `tel` on the primary and use `autocomplete="off"` (or a distinguishing hint) on the secondary field.

Location: `row-website` div
Evidence: `<label id="website-label" for="website-input">Company website</label> ... required=""`
Problem: This is a personal shopping account signup ("Meridian Outfitters account"), yet a company website is a mandatory field — an irrelevant requirement that will block individual consumers from completing signup.
Fix: Remove the field or make it optional and scoped to business/wholesale accounts only.

Location: `row-member` div
Evidence: `<input id="member-input" ... placeholder="Must be 8 digits" required="">`
Problem: The "8 digits" constraint is communicated only via placeholder text (which disappears once the user types) and is not actually enforced — there is no `pattern` or `maxlength` attribute, so any non-numeric or wrong-length value can be submitted.
Fix: Add `pattern="\d{8}"` and `maxlength="8"`, and move the format requirement into persistent helper text rather than relying solely on the placeholder.

Location: `row-acctnum` div
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label>` with no explanatory text, directly following the membership number field
Problem: It's unclear how "account number" differs from the "membership number" field just above it — two similarly-purposed numeric ID fields with no distinguishing description will confuse users about which number to enter where.
Fix: Add explanatory helper text clarifying the distinct purpose of each field, or merge them if they refer to the same identifier.

Location: `row-shipspeed` select options
Evidence: `<option>Overnight</option> <option>Next-day</option>`
Problem: "Overnight" and "Next-day" shipping are effectively the same service and listing both as distinct options will confuse users about what to pick.
Fix: Remove the duplicate option, keeping a single clearly-named option for next-day/overnight delivery.

Location: `row-legalname` div
Evidence: `<label id="legalname-label" for="legalname-input">Your name</label>` vs. earlier `<label id="name-label" for="name-input">Full name</label>`
Problem: This field duplicates the "Full name" field collected earlier in the form under a different, vaguer label, forcing the user to enter their name twice.
Fix: Remove the redundant field, or if a distinct "legal name" is truly needed, rename the label to clarify how it differs from "Full name" and explain why both are required.

Location: `row-org` div
Evidence: `<input id="org-input" name="organization" type="text" style="font-size:16px" required="">`
Problem: Like the website field, a required organization name is inappropriate for an individual consumer retail account signup and will block personal customers from completing the form.
Fix: Make the field optional or remove it from the standard consumer signup flow.

Location: `row-contacttime` div
Evidence: `<input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: "Preferred contact time" is captured as free-form text with no format guidance, placeholder, or structured control, so submitted values will be inconsistent and hard to parse (e.g. "morning" vs "9am" vs "afternoons").
Fix: Replace with a `<select>` of defined time-of-day ranges or a `type="time"` input, and/or add a placeholder showing the expected format.

Location: `viewdetails-btn` button
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>`
Problem: This button has `type="button"` (so it won't submit the form) but the document contains no `<script>` wiring up any click handler, making it a non-functional dead control sitting right next to the submit button.
Fix: Either implement the intended behavior with a script, or remove the button if it serves no purpose.

Location: throughout the form (`org-input`, `contacttime-label`, `viewdetails-btn`)
Evidence: `style="font-size:16px"`, `style="display:block"`, `style="padding:12px 20px;font-size:16px"`
Problem: Inline styles are applied ad hoc to only three elements while the rest of the form has no styling at all (no `<style>` or stylesheet link), producing inconsistent presentation.
Fix: Move styling into a shared stylesheet or `<style>` block applied consistently across all form rows instead of one-off inline styles.
