Location: `<head>` section (lines 3–5)
Evidence: `<meta charset="utf-8">` is present but there is no `<meta name="viewport" content="width=device-width, initial-scale=1">`
Problem: Without a viewport meta tag, mobile browsers will render the form at desktop width and auto-zoom, and the later inline `font-size:16px` hack (meant to prevent iOS zoom-on-focus) has no effect without it.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the `<head>`.

Location: `row-street` div
Evidence: `<input id="street-input" name="street_address" type="text" autocomplete="address-line1" ... required="">` with no accompanying city, state/region, or country fields
Problem: The address is collected as a single street line plus a later, disconnected postal-code field, with no way to capture city, state, or country — incomplete for shipping an order.
Fix: Add city, state/region, and country fields (with `autocomplete="address-level2"`, `address-level1`, `country"`) grouped with street address and postal code.

Location: `row-phone2` div
Evidence: `<input id="phone2-input" name="phone_secondary" type="tel" autocomplete="tel">` — identical to the primary phone field's `autocomplete="tel"`
Problem: Both the primary and secondary phone inputs share the same `autocomplete="tel"` token, so browsers can't distinguish them and may autofill the same number into both.
Fix: Differentiate the fields, e.g. wrap each in a `<fieldset>` with distinct autocomplete scoping, or drop autocomplete from the secondary field.

Location: `row-website` div
Evidence: `<label id="website-label" for="website-input">Company website</label> ... required=""`
Problem: A "Company website" field is a business/B2B field with no apparent relevance to a consumer apparel account signup, and it's marked required, blocking ordinary customers from completing signup.
Fix: Remove the field, or make it optional and only show it for business accounts.

Location: `row-member` div
Evidence: `<input id="member-input" ... inputmode="numeric" placeholder="Must be 8 digits" required="">`
Problem: The "must be 8 digits" instruction exists only as placeholder text, which disappears once the user starts typing, and there's no `pattern`/`maxlength` to actually enforce or validate the 8-digit requirement.
Fix: Add `maxlength="8"` and `pattern="\d{8}"`, and move the format instruction into persistent helper text (like the phone field's `<p>`) rather than relying solely on the placeholder.

Location: `row-acctnum` div
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label>` immediately follows the "Membership number (8 digits)" field
Problem: "Account number" and "Membership number" appear to refer to the same concept with no explanation of how they differ, and account number has no autocomplete attribute or format guidance at all.
Fix: Either merge these into one field or add label/help text clarifying the distinct purpose of each, and add appropriate validation/autocomplete attributes.

Location: `row-shipspeed` div
Evidence: `<select id="shipspeed-select" required="">` has no `name` attribute
Problem: Without a `name` attribute, the selected shipping speed will not be included in the submitted form data at all.
Fix: Add `name="shipping_speed"` to the `<select>` element.

Location: `row-shipspeed` div
Evidence: `<option>Overnight</option> <option>Next-day</option>`
Problem: "Overnight" and "Next-day" describe the same delivery speed, creating a confusing duplicate choice for users.
Fix: Remove one of the two redundant options (or rename to clearly distinct tiers, e.g. "Next-day" vs "Same-day").

Location: `row-legalname` div
Evidence: `<label id="legalname-label" for="legalname-input">Your name</label> ... autocomplete="name" ... required=""`, compared to `row-name`'s `<label id="name-label" for="name-input">Full name</label>`
Problem: This field duplicates the "Full name" field collected earlier in the form (same `autocomplete="name"`), forcing the user to enter their name twice with no explanation of why two name fields exist.
Fix: Remove this duplicate field, or rename/clarify its purpose if it's meant to capture something different (e.g. a legal name differing from a preferred name) and explain that distinction in the label.

Location: `row-org` div
Evidence: `<input id="org-input" name="organization" type="text" style="font-size:16px" required="">`
Problem: This input has an inline style not applied consistently to any other input in the form, and the field is required despite the form otherwise targeting individual consumers, not organizations.
Fix: Move styling into a shared stylesheet/rule applied consistently to all inputs, and make "Organization name" optional (or remove it) for a consumer signup.

Location: `row-contacttime` div
Evidence: `<label id="contacttime-label" for="contacttime-input" style="display:block">Preferred contact time</label><input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: "Preferred contact time" is captured as unconstrained free text, which will produce inconsistent, unparseable data, and the label has a one-off inline style not used elsewhere.
Fix: Replace the free-text input with a `<select>` of time ranges (e.g. Morning/Afternoon/Evening) or a `<input type="time">`, and move the `display:block` styling to shared CSS.

Location: `viewdetails-btn` button
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>` placed directly before the submit button, with no script or handler anywhere in the document
Problem: This button has no associated behavior (no `onclick`, no JS elsewhere in the document), so clicking it does nothing, and its prominent inline styling next to "Create account" risks misleading users about which button completes signup.
Fix: Either implement its intended behavior with a script, or remove the button if it serves no function.

Location: `<form id="form">` opening tag
Evidence: `<form id="form">` has no `action` or `method` attribute
Problem: Without `action`/`method`, submitting the form has no defined destination or HTTP verb, so the account data cannot actually be sent anywhere absent additional (unshown) JavaScript.
Fix: Add `method="post"` and `action="/signup"` (or the appropriate endpoint), or document that submission is handled entirely via a `submit` event listener.
