Location: `<form id="form">` opening tag
Evidence: `<form id="form">` has no `action` or `method` attribute
Problem: Without `method="post"`, the form defaults to GET, so the password and password-confirmation fields would be submitted as plaintext query-string parameters, exposing them in browser history, server logs, and the Referer header.
Fix: Add `method="post"` and an `action` pointing to the registration endpoint.

Location: row-email, `email-input`
Evidence: `autocomplete="e-mail"`
Problem: `e-mail` is not a valid HTML autocomplete token (the correct value is `email`), so browsers will not reliably autofill this field.
Fix: Change `autocomplete="e-mail"` to `autocomplete="email"`.

Location: row-confirm-password, `confirm-password-input`
Evidence: `<input id="confirm-password-input" name="password_again" type="password" autocomplete="new-password" required="">` with no script anywhere in the document
Problem: There is no `minlength` on this field (inconsistent with the primary password field) and no client-side mechanism at all to verify the two password fields match, since the document contains no `<script>`.
Fix: Add `minlength="8"` to the confirm field and add JavaScript (or a `pattern`-based workaround) to validate that the two password values match before submit.

Location: row-phone, `phone-input` and its helper `<p>`
Evidence: `<input id="phone-input" ...><p>We will text you about delivery updates.</p>`
Problem: The explanatory text is not programmatically associated with the input, so screen reader users won't know it relates to the phone field.
Fix: Give the `<p>` an `id` and reference it from the input via `aria-describedby`.

Location: row-housenumber, `housenumber-input`
Evidence: `<input id="housenumber-input" name="house_number" type="text" required="">` (no `autocomplete` attribute), compared with the following `street-input` which has `autocomplete="address-line1"`
Problem: The missing autocomplete token breaks address autofill continuity between house number and street address.
Fix: Add an appropriate autocomplete value (e.g. combine house number into `address-line1`/`address-line2` or add `autocomplete="address-line2"`).

Location: row-website, `website-input`
Evidence: `<label ...>Company website</label><input ... name="website" type="url" required="">`
Problem: A required company website field is out of place and creates unnecessary friction on a consumer apparel retailer's personal account signup form.
Fix: Remove this field or make it optional and clarify why a personal shopper would need to provide a company website.

Location: row-member, `member-input`
Evidence: `placeholder="Must be 8 digits"` with no `pattern` or `maxlength` attribute
Problem: The 8-digit format requirement is communicated only via placeholder text, which disappears once the user types and provides no enforced validation.
Fix: Add `pattern="\d{8}"` and `maxlength="8"`, and move the format hint into persistent visible helper text.

Location: row-acctnum, `acctnum-input`
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label><input ... name="account_number" type="text" inputmode="numeric" required="">`
Problem: This required field's purpose overlaps with the adjacent "Membership number" field with no distinguishing help text, confusing users about what to enter.
Fix: Either remove the redundant field or add clear, distinct helper text explaining how account number differs from membership number.

Location: row-shipspeed, `shipspeed-select` options
Evidence: `<option>Overnight</option><option>Next-day</option><option>International</option>`
Problem: "Overnight" and "Next-day" describe the same shipping speed, and "International" is a destination, not a speed, so the option set conflates two different categories.
Fix: Remove the duplicate overnight/next-day option and move "International" to a separate shipping-destination field.

Location: row-shipspeed, `shipspeed-select`
Evidence: `<select id="shipspeed-select" required="">` with `<option>Standard</option>` listed first and no blank/placeholder option
Problem: Because the first option is selected by default and is a valid value, the `required` attribute has no practical effect — the user can submit without ever making a choice.
Fix: Add a disabled, selected placeholder option (e.g. "Select shipping speed") so `required` actually forces a deliberate choice.

Location: row-legalname, `legalname-input`
Evidence: `<label id="legalname-label" for="legalname-input">Your name</label><input ... name="legal_name" type="text" autocomplete="name" ... required="">`
Problem: This duplicates the "Full name" field collected earlier (`name-input`), using the same `autocomplete="name"` token, which will confuse users and autofill behavior by asking for the same information twice under different labels.
Fix: Remove one of the two name fields, or clearly differentiate their purposes (e.g. "legal name" vs. "display name") with distinct labeling and autocomplete tokens.

Location: row-org, `org-input`
Evidence: `<input id="org-input" name="organization" type="text" style="font-size:16px" required="">`
Problem: A required organization name field is scope creep for a personal retail account, and the one-off inline `style` attribute suggests ad hoc patching rather than a consistent stylesheet rule (other text inputs lack it despite presumably needing the same iOS zoom fix).
Fix: Remove the organization field (or make it optional) and move `font-size: 16px` into a shared CSS rule applied to all text inputs.

Location: row-contacttime, `contacttime-label`
Evidence: `<label id="contacttime-label" for="contacttime-input" style="display:block">Preferred contact time</label><input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: The field is a required free-text input with no format guidance (e.g. "10am–12pm" vs "morning"), making responses inconsistent and hard to process; the inline `display:block` style is another one-off patch rather than a stylesheet rule.
Fix: Replace the free-text input with a `<select>` or `<input type="time">`/range picker, and move the display style into CSS.

Location: `viewdetails-btn`
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>`
Problem: The button has no visible target, `aria-controls`/`aria-expanded`, or accompanying script, so its purpose and behavior are undefined within the document.
Fix: Either remove the button or wire it to a specific action/disclosure with appropriate ARIA attributes describing what it reveals.

Location: row-hear, `hear-select`
Evidence: `<select id="hear-select" required="">` with `<option>Search engine</option>` listed first and no blank/placeholder option
Problem: As with the shipping-speed select, the pre-selected first option makes the `required` attribute ineffective at forcing an actual choice.
Fix: Add a disabled, selected placeholder option so the field cannot be submitted without an intentional selection.

Location: `<head>` section
Evidence: `<meta charset="utf-8"><title>Create your Meridian Outfitters account</title>` (no viewport meta tag)
Problem: The document has no `<meta name="viewport">` tag, so on mobile devices this form (which includes phone, address, and password fields) will render at desktop scale and be hard to use.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the `<head>`.
