Location: `<head>` section
Evidence: `<meta charset="utf-8">` followed directly by `<title>Join Meridian Outfitters</title>` with no other meta tags
Problem: There is no viewport meta tag, so the form will not scale correctly on mobile browsers and may render zoomed out or with incorrect tap-target sizing.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the `<head>`.

Location: `<form id="form">` opening tag
Evidence: `<form id="form">`
Problem: The form has no `action` or `method` attribute, so a native (non-JS) submission has no defined destination or HTTP verb.
Fix: Add explicit `action="/signup"` and `method="post"` attributes (or document that submission is handled entirely via JavaScript).

Location: row-website (`Company website`)
Evidence: `<input id="website-input" name="website" required="" type="text">`
Problem: A personal "Join" signup form forces every user to supply a company website, which doesn't apply to individual customers, and the field uses `type="text"` instead of `type="url"`, so no URL format is validated even when one is entered.
Fix: Make the field optional (or remove it for a consumer signup flow) and change `type="text"` to `type="url"`.

Location: row-member (`Membership number (8 digits)`)
Evidence: `placeholder="Must be 8 digits"` with no `pattern` or `maxlength` attribute on `#member-input`
Problem: The 8-digit requirement is communicated only through placeholder text, which disappears once typing starts, and is not enforced by any `pattern`/`maxlength`, so non-conforming values can be submitted. It's also contradictory to require an existing membership number on a form titled "Create your account"/"Join."
Fix: Add `pattern="[0-9]{8}"` and `maxlength="8"`, move the format hint into persistent helper text, and clarify whether this field only applies to existing members (making it optional otherwise).

Location: row-acctnum (`Account number`)
Evidence: `<input id="acctnum-input" name="account_number" type="text" inputmode="numeric" required="">`
Problem: A brand-new signup form requiring a mandatory "Account number" is both unexplained (account number for what system?) and has no format constraint despite being numeric, and asking for this on account creation reads as a sensitive/suspicious data request with no stated purpose.
Fix: Either remove this field or add explanatory text about what it refers to, make it optional if not universally applicable, and add a `pattern`/`maxlength` matching the expected format.

Location: row-postal (`Postal code`)
Evidence: `<input id="postal-input" name="postal_code" type="text" autocomplete="postal-code" required="" size="3">`
Problem: `size="3"` renders a visible input box of only ~3 characters, far too small for most postal codes (e.g., 5-digit US ZIP codes or longer alphanumeric UK/Canadian postcodes), causing poor usability.
Fix: Remove the `size` attribute or increase it to at least 10, and let CSS control width instead.

Location: row-shipspeed (`Preferred shipping speed`)
Evidence: `<option>Standard</option><option>Express</option><option>Overnight</option><option>Next-day</option><option>International</option>`
Problem: "Overnight" and "Next-day" are overlapping/duplicate concepts, and "International" describes a destination, not a shipping speed, making the option set internally inconsistent.
Fix: Collapse "Overnight"/"Next-day" into one option and move "International" to a separate shipping-destination field (or remove it from this list).

Location: row-legalname (`Your name`)
Evidence: `<input id="legalname-input" name="legal_name" type="text" autocomplete="name" ...>` duplicating `<input id="name-input" name="full_name" type="text" autocomplete="name" ...>` in row-name
Problem: Two separate required fields both collect the user's name with identical `autocomplete="name"`, which is redundant, will confuse browser autofill (both may populate from the same source), and burdens the user with entering the same data twice.
Fix: Remove one of the two name fields, or rename/repurpose "legal_name" with a distinct `autocomplete` value (e.g., `off`) and a label that clarifies why it differs from "Full name."

Location: row-org (`Organization name`)
Evidence: `<input id="org-input" name="organization" type="text" required="" style="font-size:13px">`
Problem: This input is styled with a smaller font size than every other field on the form via an inline style, creating inconsistent visual hierarchy and reduced legibility.
Fix: Remove the inline `style="font-size:13px"` and let it inherit the same font size as other inputs.

Location: row-contacttime (`Preferred contact time`)
Evidence: `<label id="contacttime-label" for="contacttime-input" style="display:inline-block;float:left;width:140px">Preferred contact time</label>` followed by `<input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: This is a required free-text field with no format guidance (e.g., no placeholder, pattern, or time picker), inviting inconsistent data like "mornings" vs "9am-12pm"; additionally its label uses one-off inline float/width styling not used by any other label in the form.
Fix: Replace the free-text input with a `<select>` of defined time ranges (consistent with the shipping-speed pattern), and remove the inline style in favor of the same styling approach used by other labels.

Location: `#viewdetails-btn`
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>` placed directly between row-contacttime and the row-dob fieldset, with no surrounding row div and no script in the document wiring it up
Problem: This button has no associated behavior anywhere in the document (it's `type="button"` with no handler), so clicking it does nothing; it also breaks the form's consistent div-per-field structure and sits oddly among input rows right before the submit button, risking accidental clicks.
Fix: Either implement its intended behavior (e.g., a details modal/toggle) or remove it; if kept, wrap it in a row div consistent with other elements and move it away from the submit flow.

Location: row-dob, `#dob-year-select`
Evidence: year options list only `1950` through `2009`
Problem: This arbitrarily excludes any customer born before 1950 (age 76+ in 2026) and anyone born after 2009, incorrectly preventing valid adult customers from completing signup.
Fix: Generate the year list dynamically relative to the current year (e.g., current year minus 100 through current year minus a minimum age threshold) instead of a hardcoded range.
