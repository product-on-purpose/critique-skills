Location: row-email, `<input id="email-input" ...>`
Evidence: `autocomplete="e-mail"`
Problem: "e-mail" is not a valid HTML autocomplete token (the correct value is "email"), so browsers will not reliably autofill this field.
Fix: Change `autocomplete="e-mail"` to `autocomplete="email"`.

Location: row-confirm-password, `<input id="confirm-password-input" ...>`
Evidence: `<input id="confirm-password-input" name="password_again" type="password" autocomplete="new-password" required="">`
Problem: Unlike the password field, this input has no `minlength="8"`, so a user could type a confirmation shorter than the minimum password length with no immediate feedback that something is off.
Fix: Add `minlength="8"` to the confirm-password input to match the password field.

Location: row-housenumber, `<input id="housenumber-input" ...>`
Evidence: `<input id="housenumber-input" name="house_number" type="text" required="">`
Problem: Requiring a separate, mandatory "house number" field blocks users whose address has no numbered house (rural addresses, PO boxes, many non-US formats).
Fix: Make the field optional, or fold it into the street-address field instead of requiring it separately.

Location: row-phone2, `<input id="phone2-input" ...>`
Evidence: Both `phone-input` and `phone2-input` use `autocomplete="tel"`
Problem: Using the identical autocomplete token for both the primary and secondary phone fields can cause browsers to autofill the same number into both, defeating the purpose of a "secondary" phone.
Fix: Differentiate the tokens, e.g. use `autocomplete="tel"` for the primary and a non-autofilled or `tel-extension`/custom token for the secondary field.

Location: row-website, `<input id="website-input" ...>`
Evidence: `<label ...>Company website</label>` ... `<input id="website-input" name="website" type="url" required="">`
Problem: A required "company website" field is out of place on a consumer retail account signup (Meridian Outfitters) and will block individual customers who have no company website.
Fix: Remove the field, or make it optional and clearly scoped to business accounts only.

Location: row-member, `<input id="member-input" ...>`
Evidence: `placeholder="Must be 8 digits"` with no `pattern` or `maxlength` attribute
Problem: The "8 digits" requirement is only communicated via placeholder text (which disappears on input) and is not actually enforced, so users can submit the wrong length or non-numeric characters.
Fix: Add `pattern="\d{8}"` and `maxlength="8"` to enforce the stated format.

Location: row-acctnum, `<input id="acctnum-input" ...>`
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label>` with no helper text
Problem: It's unclear what "account number" means for someone who is creating a new account for the first time, and unlike the phone field there's no explanatory text.
Fix: Add helper text clarifying the field's purpose (e.g., an existing loyalty/catalog account number), or remove it if not needed at signup.

Location: row-postal, `<input id="postal-input" ...>`
Evidence: `<input id="postal-input" name="postal_code" type="text" autocomplete="postal-code" required="">` — no corresponding country field anywhere in the form
Problem: Postal code format and validity depend on country, but the form never collects a country, which is especially inconsistent given "International" is offered as a shipping option.
Fix: Add a required country field (e.g., a `select` with `autocomplete="country"`) before or alongside the postal code field.

Location: row-shipspeed, `<select id="shipspeed-select">`
Evidence: `<option>Overnight</option>\n <option>Next-day</option>` and `<option>International</option>`
Problem: "Overnight" and "Next-day" are redundant options that will confuse users, and "International" conflates a shipping destination with a shipping speed.
Fix: Remove the duplicate "Next-day"/"Overnight" option and move "International" out of this speed selector into a destination/country-driven field.

Location: row-legalname, `<input id="legalname-input" ...>`
Evidence: `<label id="legalname-label" for="legalname-input">Your name</label> ... autocomplete="name"` versus the earlier `row-name` field `<label id="name-label" for="name-input">Full name</label> ... autocomplete="name"`
Problem: The form asks for the user's name twice (full_name and legal_name), both marked `autocomplete="name"`, which is redundant and may cause browser autofill to populate them inconsistently.
Fix: Remove the duplicate "Your name" field, or rename/repurpose it to clarify how it differs from "Full name" (e.g., legal name for billing vs. display name).

Location: row-org, `<input id="org-input" ...>`
Evidence: `<label id="org-label" for="org-input">Organization name</label>` ... `required=""`
Problem: A required organization name field is inappropriate for an individual consumer creating a retail account and forces non-business users to invent a value.
Fix: Make the field optional and only show/require it for business account signups.

Location: row-contacttime, `<input id="contacttime-input" ...>`
Evidence: `<input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: A free-text required field for "preferred contact time" gives no format guidance, so submissions will be inconsistent ("morning", "9am", "anytime") and hard to use programmatically.
Fix: Replace with a `<select>` of discrete time ranges or a `type="time"` input, and remove the hard requirement.

Location: viewdetails-btn, `<button id="viewdetails-btn" type="button" ...>`
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>` — document contains no `<script>` element
Problem: The button has `type="button"` (so it won't submit the form) but there is no JavaScript anywhere in the document to give it behavior, making it a dead control.
Fix: Either remove the button or add the script/handler that implements its "View details" behavior.

Location: row-hear, `<select id="hear-select">`
Evidence: `<select id="hear-select" required="">` for "How did you hear about us?"
Problem: Marketing-attribution questions are not essential to account creation and requiring an answer adds friction/blocks submission for users who don't fit the listed options.
Fix: Remove the `required` attribute from this select.

Location: Throughout the form (e.g. org-input, contacttime-label, viewdetails-btn)
Evidence: `style="font-size:16px"`, `style="display:block"`, `style="padding:12px 20px;font-size:16px"`
Problem: Styling is applied ad hoc via inline `style` attributes on only a few scattered elements rather than consistently through CSS, making the presentation inconsistent and hard to maintain.
Fix: Move these styles into a stylesheet with classes applied consistently across equivalent elements.

Location: Overall form structure (`<form id="form">`)
Evidence: No `<fieldset>`/`<legend>` elements anywhere in the document
Problem: Related fields (e.g. house number, street, postal code) are not grouped semantically, which hurts accessibility and makes the long flat list of fields harder to scan.
Fix: Wrap related field groups (name/contact, address, account/shipping preferences) in `<fieldset>` elements with descriptive `<legend>` labels.
