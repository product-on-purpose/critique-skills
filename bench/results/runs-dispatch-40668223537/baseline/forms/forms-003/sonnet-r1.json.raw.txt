Location: `<head>` section
Evidence: `<meta charset="utf-8">` followed directly by `<title>Join Meridian Outfitters</title>` with no other meta tags
Problem: There is no `<meta name="viewport" content="width=device-width, initial-scale=1">` tag, so on mobile browsers the page will render at desktop width and inputs will trigger zoom-on-focus.
Fix: Add a viewport meta tag to the `<head>`.

Location: `<form id="form">` opening tag
Evidence: `<form id="form">`
Problem: The form has no `action` or `method` attribute, so submitting it will reload the current page with a GET request instead of sending data anywhere.
Fix: Add `action="/signup"` (or appropriate endpoint) and `method="post"`.

Location: row-password, password-input
Evidence: `minlength="6"`
Problem: A 6-character minimum is weaker than modern guidance (e.g. NIST SP 800-63B recommends at least 8 characters), giving users a false sense of adequate password strength.
Fix: Raise `minlength` to at least 8 and consider surfacing a strength indicator instead of relying solely on length.

Location: row-phone
Evidence: `<p>Thanks for signing up.</p>`
Problem: A "thank you" confirmation message is rendered inline inside the phone-number field row before the form has been submitted, which is confusing and appears to be leftover/misplaced content.
Fix: Remove this paragraph from the phone row, or move it to a post-submit confirmation view.

Location: row-phone and row-phone2
Evidence: both `phone-input` and `phone2-input` use `autocomplete="tel"`
Problem: Using the identical autocomplete token for both the primary and secondary phone fields can cause browsers to autofill the same number into both inputs.
Fix: Disambiguate with section tokens, e.g. `autocomplete="tel"` for the primary and `autocomplete="section-secondary tel"` for the secondary field.

Location: row-website, website-input
Evidence: `<input id="website-input" name="website" type="url" required="">`
Problem: Requiring a company website to create a personal membership account is an unnecessary hard requirement that will block individual users who have none.
Fix: Make the website field optional (remove `required`) unless the account type genuinely demands it.

Location: row-member, member-input
Evidence: `placeholder="Must be 8 digits"` with no `pattern` or `maxlength` attribute
Problem: The format requirement is communicated only via placeholder text (which disappears once the user types) and is not actually enforced by any validation attribute, so an incorrectly-formatted value can still pass.
Fix: Add `pattern="\d{8}"` and `maxlength="8"`, and move the instruction into visible helper text rather than relying solely on the placeholder.

Location: row-acctnum, acctnum-input
Evidence: `<input id="acctnum-input" name="account_number" type="text" required="">` immediately following the required `membership_number` field
Problem: The form requires both a "membership number" and an "account number" with no explanation of how they differ, which is confusing on a signup form where neither may exist yet for a new user.
Fix: Either clarify the distinction with helper text or remove one of the two redundant identifier fields.

Location: row-postal
Evidence: row-postal appears after row-acctnum and before row-shipspeed, separated from row-street by five unrelated fields
Problem: Postal code is logically part of the mailing address and should be grouped with street address, but it's placed far away, hurting form scannability and autofill grouping.
Fix: Move row-postal to immediately follow row-street.

Location: row-shipspeed, shipspeed-select
Evidence: `<select id="shipspeed-select" required="">`
Problem: The `<select>` element has no `name` attribute, so its selected value will not be included in the submitted form data at all.
Fix: Add `name="shipping_speed"` to the select element.

Location: row-legalname
Evidence: `given-input` (First name) and `family-input` (Last name) appear as separate required fields after `name-input` (Full name) was already collected
Problem: The form collects the user's name twice in incompatible formats (one free-text full name field, one split first/last name fields) with no indication of why both are needed, risking inconsistent data and user confusion.
Fix: Remove the duplicate full-name field and keep only one name-collection scheme (either a single full name field or split given/family fields).

Location: row-org, org-input
Evidence: `style="font-size:16px"` on `org-input` only
Problem: This single input has an inline font-size override not applied to any other input in the form, creating inconsistent styling and suggesting a mobile-zoom workaround that isn't applied consistently elsewhere.
Fix: Apply a consistent base font-size (e.g. 16px) to all inputs via shared CSS rather than an inline style on one field.

Location: row-contacttime, contacttime-input
Evidence: `<input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: A free-text input with no placeholder, pattern, or format hint is used to capture "preferred contact time," which will produce inconsistent, unparseable data.
Fix: Use a `type="time"` input or a `<select>` of predefined time windows instead of unconstrained free text.

Location: viewdetails-btn
Evidence: `style="padding:1px 2px;font-size:11px"`
Problem: The button's padding and font size make its tap target far smaller than accessible touch-target guidelines (e.g. WCAG 2.5.5 recommends at least 44x44px), making it hard to tap on mobile.
Fix: Increase padding and font-size to meet a minimum ~44x44px touch target.

Location: viewdetails-btn
Evidence: `<button id="viewdetails-btn" type="button" style="padding:1px 2px;font-size:11px">View details</button>` with no `<script>` anywhere in the document
Problem: The button is `type="button"` (so it does not submit) but there is no JavaScript anywhere in the document to give it any behavior, making it a dead control.
Fix: Either add the script that wires up this button's intended action, or remove the button if it has no current purpose.

Location: end of form, submit-btn and reset-btn
Evidence: `<button id="submit-btn" type="submit">Create account</button>\n  <button id="reset-btn" type="reset">Clear form</button>`
Problem: Placing a reset button directly next to the submit button is a well-known UX anti-pattern that risks users accidentally wiping all entered data.
Fix: Remove the reset button, or visually separate/de-emphasize it and require a confirmation before clearing the form.
