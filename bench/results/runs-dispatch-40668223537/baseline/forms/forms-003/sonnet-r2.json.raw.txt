Location: `row-phone` div, inside the phone number field
Evidence: `<p>Thanks for signing up.</p>`
Problem: A post-submission thank-you message is hard-coded into the middle of the form, before the user has submitted anything.
Fix: Remove this paragraph from the form body and show a thank-you message only after successful submission.

Location: `password-input` in `row-password`
Evidence: `minlength="6"`
Problem: A 6-character minimum with no complexity requirement is a weak password policy, and no visible hint tells the user any requirement exists.
Fix: Raise the minimum (e.g. 8+ characters), and add visible helper text near the field describing the requirement.

Location: `website-input` in `row-website`
Evidence: `<input id="website-input" name="website" type="url" required="">`
Problem: "Company website" is marked required on what appears to be an individual membership signup, which will block anyone without a company site from completing the form.
Fix: Make this field optional, or remove it if it isn't actually needed for individual membership.

Location: `member-input` in `row-member`
Evidence: `placeholder="Must be 8 digits"` with no `pattern`, `minlength`, or `maxlength`
Problem: The 8-digit requirement is communicated only via placeholder text (which disappears once the user types) and isn't enforced by any validation attribute.
Fix: Add `pattern="\d{8}"` plus `minlength="8" maxlength="8"`, and move the instruction into persistent helper text rather than relying on the placeholder alone.

Location: `acctnum-input` in `row-acctnum`
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label>` required on an account-creation form
Problem: Requiring an "account number" on a form whose purpose is to create the account is contradictory — the user doesn't have one yet.
Fix: Remove this field, or clarify what it refers to (e.g. an existing loyalty/customer number) and make it optional.

Location: `row-name` vs `row-legalname`
Evidence: `name="full_name"` ... later `name="given_name"` / `name="family_name"`
Problem: The form collects the user's name twice in two different, potentially inconsistent formats (one combined field, one split pair).
Fix: Pick one representation of name and remove the other.

Location: `row-legalname` div
Evidence: Two `<label>`/`<input>` pairs (`given-input`, `family-input`) inside a single row div, unlike every other row which holds exactly one field
Problem: This breaks the one-field-per-row convention used everywhere else in the form, making the markup structurally inconsistent.
Fix: Split into two separate row divs (e.g. `row-given`, `row-family`) matching the pattern used elsewhere.

Location: `org-input` in `row-org`
Evidence: `style="font-size:16px"` present only on this input
Problem: This looks like a fix for the mobile-Safari auto-zoom bug (inputs under 16px trigger zoom on focus), but it's applied to only one field, leaving every other text input susceptible to the same issue.
Fix: Apply a consistent minimum font-size (via a shared stylesheet rule, not scattered inline styles) to all text inputs.

Location: `viewdetails-btn`
Evidence: `style="padding:1px 2px;font-size:11px"`
Problem: This tap target is far below accessible minimum size guidelines (effectively a few pixels), making it very hard to tap reliably, especially on touch devices.
Fix: Increase padding/font-size to meet at least a 24x24px (ideally 44x44px) touch target.

Location: `viewdetails-btn`
Evidence: `<button id="viewdetails-btn" type="button" ...>View details</button>` with no `<script>` anywhere in the document
Problem: The button has no attached behavior since the document contains no JavaScript at all, so it is currently a dead control.
Fix: Either add the script that gives this button a function, or remove it until that logic exists.

Location: Address fields overall (`row-street`, `row-postal`)
Evidence: Only `street_address` and `postal_code` fields exist; no city, state/region, or country field
Problem: The address collected is incomplete for shipping purposes, yet the form also asks for a "Preferred shipping speed" (`row-shipspeed`), implying physical shipment.
Fix: Add city and state/region (and country, if international) fields alongside street address and postal code.

Location: `<form id="form">` opening tag
Evidence: `<form id="form">` — no `action` or `method` attribute
Problem: Without `action`/`method`, the form's submission destination and HTTP method are undefined, so submit behavior depends entirely on unseen JS.
Fix: Add explicit `action` and `method` attributes, or confirm and document the JS handler that intercepts submission.

Location: `submit-btn` and `reset-btn`
Evidence: `<button id="submit-btn" type="submit">Create account</button>` immediately followed by `<button id="reset-btn" type="reset">Clear form</button>`
Problem: Placing a reset button directly next to the submit button risks accidental full data loss from a single misclick after filling out a long form.
Fix: Remove the reset button, or visually separate/de-emphasize it and add a confirmation step before clearing.

Location: `contacttime-input` in `row-contacttime`
Evidence: `<input id="contacttime-input" name="contact_time" type="text" required="">`
Problem: Using a free-text field for "Preferred contact time" invites inconsistent, unparseable values (e.g. "morning" vs "9am" vs "AM").
Fix: Replace with a `<select>` of defined time ranges or an `<input type="time">`/structured control.

Location: Field order across the form (`row-street` vs `row-postal`)
Evidence: Street address appears right after the password field, while postal code appears much later, separated by phone, phone2, website, membership number, and account number
Problem: Splitting the two address-related fields apart with several unrelated fields in between makes the form's logical grouping confusing to fill out.
Fix: Move `row-postal` to immediately follow `row-street` (and add city/state fields there too) so address information is grouped together.
