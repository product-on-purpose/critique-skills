Location: <head> (lines 3–6)
Evidence: `<meta charset="utf-8">` is the only meta tag present
Problem: There is no `<meta name="viewport">` tag, so the form will not scale or lay out correctly on mobile browsers.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the `<head>`.

Location: `<title>` vs `<h1>`
Evidence: Title is "Create your Meridian Outfitters account" but the on-page heading is "Set up your account"
Problem: The page title and the visible heading use different wording for the same action, which can read as inconsistent branding/copy.
Fix: Make the `<h1>` text match (or closely mirror) the `<title>`, e.g. "Create your Meridian Outfitters account."

Location: row-phone and row-phone2 inputs
Evidence: Both `phone-input` and `phone2-input` use `autocomplete="tel"`
Problem: Two fields sharing the same autocomplete token causes browsers to autofill the same phone number into both the primary and "secondary" phone fields.
Fix: Give the secondary field a distinct token, e.g. `autocomplete="tel-national"` or omit autocomplete on the secondary field entirely.

Location: row-website
Evidence: `<label ...>Company website</label> <input ... name="website" type="url" required="">`
Problem: A required "company website" field is out of place on a consumer outfitters account signup and will block individual customers who have no company/website from ever completing registration.
Fix: Remove the field, or make it optional and only show/require it for business accounts.

Location: row-member
Evidence: `<input id="member-input" name="membership_number" type="text" inputmode="numeric" placeholder="Must be 8 digits" required="">`
Problem: The "8 digits" constraint is only communicated via placeholder text (which disappears on input) and is not enforced with `pattern`/`maxlength`, so invalid lengths can be submitted.
Fix: Add `pattern="\d{8}"` and `maxlength="8"` and move the digit requirement into persistent helper text rather than relying solely on the placeholder.

Location: row-acctnum
Evidence: `<label id="acctnum-label" for="acctnum-input">Account number</label>`
Problem: "Account number" has no explanatory text, and since the user hasn't created an account yet, it's unclear what number they're supposed to supply here — the field's purpose is ambiguous and it's required.
Fix: Either remove the field (it appears to duplicate "Membership number") or add helper text clarifying what account number is expected and where to find it.

Location: Address section (row-street through row-postal)
Evidence: Only "Street address" and "Postal code" fields exist; no city, state/province, or country field
Problem: The address is incomplete — most shipping addresses require a city and state/region (and country, given the "International" shipping option below), so orders cannot actually be shipped with the data collected.
Fix: Add city, state/region, and country fields with appropriate `autocomplete` values (`address-level2`, `address-level1`, `country`).

Location: row-shipspeed select options
Evidence: `<option>Express</option> <option>Overnight</option> <option>Next-day</option>`
Problem: "Overnight" and "Next-day" describe the same delivery speed, creating a confusing, overlapping choice for the user.
Fix: Remove one of the duplicate options (e.g. keep "Overnight" and drop "Next-day," or merge/rename for clarity).

Location: row-legalname
Evidence: `<label id="legalname-label" for="legalname-input">Your name</label> <input ... name="legal_name" ... autocomplete="name" ...>`
Problem: This duplicates the "Full name" field collected earlier in row-name (same `autocomplete="name"`), forcing the user to enter their name twice with no explanation of how it differs.
Fix: Remove this duplicate field, or if a distinct legal name is truly needed, relabel both fields clearly (e.g. "Preferred name" vs. "Legal name") and explain the distinction.

Location: row-org
Evidence: `<input id="org-input" name="organization" type="text" style="font-size:16px" required="">`
Problem: A required "Organization name" field is unexplained and inappropriate for an individual consumer signup, and it uses an inline style instead of a stylesheet rule, inconsistent with the rest of the form.
Fix: Make the field optional (or remove it for consumer accounts) and move `font-size:16px` into a shared CSS class/stylesheet.

Location: row-contacttime
Evidence: `<input id="contacttime-input" name="contact_time" type="text" required="">` with no placeholder or format hint
Problem: "Preferred contact time" is a free-text required field with no indication of expected format (e.g. "9am–12pm" vs "weekdays"), leading to inconsistent, unparseable data.
Fix: Replace with a `<select>` of defined time ranges, or add a `type="time"`/`placeholder` and explicit format guidance.

Location: viewdetails-btn
Evidence: `<button id="viewdetails-btn" type="button" style="padding:12px 20px;font-size:16px">View details</button>`
Problem: The button's purpose and target are undefined in the document (no associated content, link, or script reference), making it an orphan control with unclear function, and it uses inline styling instead of shared CSS.
Fix: Either remove the button or clarify what it does (e.g. link it to terms/shipping details) and move its styling into a stylesheet.

Location: row-phone helper text
Evidence: `<p>We will text you about delivery updates.</p>` with no accompanying opt-in control
Problem: The form states it will send texts but provides no consent checkbox, so SMS consent is implied/forced rather than explicitly captured, which is a compliance risk for SMS marketing/notification laws (e.g. TCPA-style consent requirements).
Fix: Add an explicit opt-in checkbox for SMS notifications separate from the required phone field, or clarify that texts are purely transactional and optional.
