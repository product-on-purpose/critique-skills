Location: `<head>` inline `<style>` block
Evidence: `@media (orientation: portrait) { #main-content { display: none; } }`
Problem: This rule hides the entire main content region whenever the viewport is in portrait orientation, which is the default orientation for virtually all phone users, making the page appear blank on mobile.
Fix: Remove this rule (or replace it with a legitimate responsive layout rule that does not hide `#main-content`).

Location: `<nav>`, link `id="nav-link1"` ("Accessibility")
Evidence: `style="outline:none"`
Problem: Removing the focus outline with no replacement focus style makes it impossible for keyboard users to see which element has focus, violating WCAG 2.4.7 — notably on the link meant to lead to the accessibility page.
Fix: Delete `style="outline:none"` or replace it with a visible custom `:focus` style.

Location: Form `id="s3-form"`, phone field

Problem: The label text tells users the field is required, but the `<input>` has neither a `required` attribute nor `aria-required="true"`, so assistive technology and browser validation won't enforce or announce it as required.

Location: Form `id="s3-form"`, promo field
Evidence: `<input id="promo" type="text" aria-invalid="true">`
Problem: `aria-invalid="true"` is hardcoded in the markup, so screen readers will announce the field as invalid immediately on page load, before the user has typed anything or submitted the form.
Fix: Remove the static `aria-invalid="true"` and set it dynamically only after validation fails.

Location: Form `id="s3-form"`, promo error text `id="s3-form-promo-error"`

Problem: The error message is not programmatically associated with the `#promo` input (no `aria-describedby`), so screen reader users won't reliably hear the error in context with the field it describes.
