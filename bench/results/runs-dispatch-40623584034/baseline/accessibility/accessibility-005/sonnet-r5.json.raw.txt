Location: `<head>` style block, `#head-style`
Evidence: `@media (orientation: portrait) { #main-content { display: none; } }`
Problem: This rule hides all main content whenever the viewport is in portrait orientation, which is the default orientation for virtually all phone users, making the page appear blank to most mobile visitors.
Fix: Remove this media query (or invert the logic if a landscape-only prompt was intended, and gate it behind a non-destructive UI rather than `display:none` on the entire main content).

Location: Header navigation, `#nav-link1`
Evidence: `<a href="/accessibility" id="nav-link1" style="outline:none">Accessibility</a>`
Problem: Removing the default focus outline strips the visible focus indicator for keyboard users on this link, which is an accessibility regression, ironically on the link to the Accessibility page.
Fix: Delete `style="outline:none"` or replace it with a visible custom `:focus-visible` style.

Location: Section "Accessibility improvements", `#s3-customcontrol`
Evidence: `style="width:16px;height:16px"` on a `role="button" tabindex="0"` delete control
Problem: A 16×16px interactive control is far below the recommended minimum touch target size (commonly 24px per WCAG 2.5.8, 44px recommended), making it hard to activate on touch devices.
Fix: Increase the clickable target to at least 24x24px (ideally 44x44px) via padding, even if the visible icon stays small.

Problem: The field is visually/textually marked required but isn't programmatically enforced or exposed as required to assistive technology, so required-field validation and announcements will be inconsistent.

Location: Section "Accessibility improvements", form input `#promo`
Evidence: `<input id="promo" type="text" aria-invalid="true">`
Problem: `aria-invalid="true"` is hardcoded in the markup before the user has interacted with or submitted the form, so screen readers will incorrectly announce this field as invalid on page load.
Fix: Set `aria-invalid="false"` (or omit it) by default, and only set it to `"true"` dynamically after a failed validation.

Location: Section "Accessibility improvements", `#s3-form-promo-error`
Evidence: `<input id="promo" ...><span class="error-text" aria-live="polite" id="s3-form-promo-error">Enter a 6 character code...</span>`
Problem: The error message is not programmatically associated with the promo input (no `aria-describedby` on `#promo` referencing `#s3-form-promo-error`), so screen reader users may not reliably hear the error tied to that field.
Fix: Add `aria-describedby="s3-form-promo-error"` to the `#promo` input.
