Location: `<title id="head-title">` vs `<h1 id="main-h1">`
Evidence: "Cascadia Regional Transit: Service Announcements" (title) vs "Fare and service announcements" (h1)
Problem: The page title and the main heading describe the page differently, which can confuse users navigating by tab title or bookmarking the page.
Fix: Align the title text with the h1, e.g. "Fare and service announcements – Cascadia Regional Transit".

Location: `<meta name="viewport" ...>` in `<head>`
Evidence: `content="width=device-width, initial-scale=1, user-scalable=no"`
Problem: `user-scalable=no` disables pinch-to-zoom, which blocks low-vision users from magnifying content and violates WCAG 1.4.4 (Resize Text).
Fix: Remove `user-scalable=no` (and any `maximum-scale` restriction) from the viewport meta tag.

Location: Section `s1`, heading "Accessibility improvements" (`#s1-h`)
Evidence: Section is titled "Accessibility improvements" but body text reads "Passengers should review the updated schedule at any station kiosk" and "Local residents may request a fare adjustment through the mobile app."
Problem: The section heading promises accessibility-related content, but the paragraphs describe schedule lookup and fare adjustments, unrelated to accessibility.
Fix: Either rewrite the paragraphs to cover actual accessibility improvements or rename the heading to match the content (e.g. "Fare and schedule updates").

Location: `#s1-p1`
Evidence: `style="color:#999999"`
Problem: Inline gray text color (#999999) on a presumably white background yields roughly 2.4:1 contrast, failing the WCAG AA 4.5:1 minimum for body text.
Fix: Remove the inline color override or replace it with a color that meets at least 4.5:1 contrast against the background.

Location: `#s1-p1` and `#s1-p2`
Evidence: Both end with the identical sentence "Updates post to the schedule page within one business day."
Problem: The same boilerplate sentence is reused for two unrelated actions (checking a kiosk schedule vs. requesting a fare adjustment), making it unclear which process it actually describes.
Fix: Write a sentence specific to each paragraph's actual action/confirmation behavior instead of reusing identical boilerplate text.

Location: `#s1-img1`

Problem: The alt text describes platform screen door inspection, which has no relation to the surrounding content about kiosks and fare adjustments in the "Accessibility improvements" section.

Location: `#s2-p1`

Location: `#s3-p2`, section "Weekend service"

Location: `#s3-banner`
Evidence: `style="width:960px"`
Problem: A fixed pixel width of 960px will overflow or get clipped on mobile viewports, especially since pinch-zoom is also disabled via the viewport meta tag, leaving no way to view the full banner.
Fix: Use a responsive width (e.g. `max-width: 960px; width: 100%;`) instead of a fixed pixel width.

Location: `#s3-statuscard`
Evidence: `style="height:60px;overflow:hidden"`
Problem: A fixed height combined with `overflow:hidden` will clip the paragraph text if it wraps to more lines than fit in 60px, hiding part of the message from users.
Fix: Remove the fixed height/overflow restriction and let the card size to its content.

Location: `#s3-statuscard`

Problem: This repeats the "Updates post to the schedule page within one business day." boilerplate from section `s1`, again attached to an unrelated action (reporting an issue vs. checking a schedule).
Fix: Write a confirmation sentence specific to submitting an issue report, not the reused schedule-update boilerplate.

Location: `#s3-button1`

Location: `#s3-linkpara` / `#s3-link1`

Location: `#s3-form`, Route field
Evidence: `<label for="topic-alt" ...>Route</label>` next to `<select id="topic">`
Problem: The label's `for` attribute references `topic-alt`, which does not exist, so the "Route" label is not programmatically associated with the select element.
Fix: Change the label's `for` attribute to `topic` to match the select's `id`.

Location: `#s3-form`, Phone field
Evidence: `<label for="phone" ...>Phone number (required)</label>` with `<input id="phone" type="tel">`
Problem: The label text states the field is required, but the input lacks a `required` or `aria-required="true"` attribute, so assistive technology and form validation won't enforce or convey that requirement.
Fix: Add `required` (or `aria-required="true"`) to the phone input.

Location: `#s3-form`, Promo code field
Evidence: `<input id="promo" type="text" aria-invalid="true">`
Problem: `aria-invalid="true"` is hardcoded on page load before the user has entered anything, causing screen readers to announce an error on an untouched, empty field.
Fix: Set `aria-invalid="false"` (or omit it) by default and only set it to `true` after validation fails.

Location: `#s3-form`, Promo code field and error text
Evidence: `<input id="promo" type="text" aria-invalid="true">` followed by `<span class="error-text" id="s3-form-promo-error">Enter a 6 character code...</span>`
Problem: The error message is not linked to the input via `aria-describedby`, so screen reader users won't hear the error explanation when focused on the field.
Fix: Add `aria-describedby="s3-form-promo-error"` to the promo input.
