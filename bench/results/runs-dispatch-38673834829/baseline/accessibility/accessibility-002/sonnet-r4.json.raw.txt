Location: `<meta name="viewport">` in `<head>`
Evidence: `content="width=device-width, initial-scale=1, user-scalable=no"`
Problem: `user-scalable=no` disables pinch-to-zoom, which prevents low-vision users from zooming the page and violates WCAG 1.4.4 (Resize Text).
Fix: Remove `user-scalable=no` (and any `maximum-scale=1`) from the viewport meta tag.

Location: Section "Accessibility improvements", paragraph `s1-p1`
Evidence: `style="color:#999999"`
Problem: Light gray text on a white background (~2.8:1 contrast ratio) fails WCAG AA minimum contrast (4.5:1) for normal text, ironically inside the "Accessibility improvements" section.
Fix: Change the text color to one with at least 4.5:1 contrast against the background (e.g. `#595959` or darker), or remove the inline style and rely on the default body text color.

Location: `s3-banner` div
Evidence: `style="width:960px"`
Problem: A fixed pixel width on a promo banner will overflow or force horizontal scrolling on narrower viewports, conflicting with the page's responsive viewport meta tag.
Fix: Replace the fixed width with a responsive unit (e.g. `max-width:960px; width:100%`).

Location: `s3-statuscard` div
Evidence: `style="height:60px;overflow:hidden"`
Problem: A fixed height combined with `overflow:hidden` will clip the enclosed paragraph text if it wraps to more lines than fit, hiding content from users.
Fix: Remove the fixed height (let it size to content) or set `min-height` instead of `height`, and drop `overflow:hidden`.

Location: Button `s3-button1`
Evidence: `style="border:1px solid #9d9d9d"`
Problem: The specified border color is low-contrast against a typical white/light background, risking failure of WCAG 1.4.11 (Non-text Contrast, 3:1 minimum) for identifying the control boundary.

Location: `s3-customcontrol` div
Evidence: `<div class="icon-delete" role="button" tabindex="0" aria-label="Delete item" id="s3-customcontrol">`
Problem: A custom `div` is reinventing a native interactive control; without a native `<button>`, keyboard activation (Enter/Space), default focus styling, and disabled-state handling all need to be reimplemented in script rather than being provided for free.
Fix: Replace with a native `<button type="button" aria-label="Delete item">` containing the icon.

Location: Form `s3-form`, Route field
Evidence: `<label for="topic-alt" id="s3-form-topic-label">Route</label>` paired with `<select id="topic">`
Problem: The label's `for` attribute ("topic-alt") doesn't match the select's `id` ("topic"), so the label is not programmatically associated with the control; clicking the label won't focus the select, and screen readers won't announce "Route" for it.
Fix: Change the label's `for` to `topic` (or change the select's `id` to `topic-alt`) so they match.

Location: Form `s3-form`, Phone field
Evidence: `<label for="phone" id="s3-form-phone-label">Phone number (required)</label>` with `<input id="phone" type="tel">`
Problem: The label text states the field is required, but the input has no `required` attribute or `aria-required="true"`, so assistive technology and browser validation won't enforce or announce the requirement.
Fix: Add `required` (and/or `aria-required="true"`) to the phone input.

Location: Form `s3-form`, Promo code field
Evidence: `<input id="promo" type="text" aria-invalid="true">`
Problem: `aria-invalid="true"` is hard-coded on page load before the user has entered anything, so screen readers will announce the empty field as invalid prematurely/incorrectly.
Fix: Set `aria-invalid="false"` (or omit it) by default, and only set it to `"true"` dynamically after a failed validation.

Location: Form `s3-form`, promo error message
Evidence: `<span class="error-text" id="s3-form-promo-error">Enter a 6 character code using letters and numbers only.</span>`
Problem: The error text is not associated with the promo input via `aria-describedby`, so screen reader users won't hear the error message when focusing or being told about the invalid field.
Fix: Add `aria-describedby="s3-form-promo-error"` to the `#promo` input.
