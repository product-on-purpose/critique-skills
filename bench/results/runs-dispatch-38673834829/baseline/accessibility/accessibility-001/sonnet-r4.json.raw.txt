Location: `<html>` opening tag
Evidence: `lang="translanguage"`
Problem: "translanguage" is not a valid BCP 47 language code, so assistive technology and browsers cannot determine the page's language.
Fix: Set `lang` to the actual content language, e.g. `lang="en"`.

Location: `<title id="head-title">` in `<head>`
Evidence: `<title id="head-title"></title>`
Problem: The title element is empty, so the browser tab, history, bookmarks, and screen readers have no page name to announce.
Fix: Add a descriptive title, e.g. "Rider Service Updates".

Location: `<img src="/img/platform-update.jpg" id="s1-img1">` in section s1
Evidence: `<img src="/img/platform-update.jpg" id="s1-img1">`
Problem: The image has no `alt` attribute, so screen reader users get no description of its content or purpose.
Fix: Add an `alt` attribute describing the image, or `alt=""` if it is purely decorative.

Location: s1-p1 and s1-p2
Evidence: Both paragraphs end with "Station staff can also help with the same request in person."
Problem: The identical closing sentence is reused for two unrelated requests (fare adjustment vs. checking real-time arrivals at a kiosk), and makes no sense for the kiosk case since the kiosk is already an in-person option.
Fix: Write a distinct, relevant closing sentence for each paragraph, or remove it from s1-p2.

Location: s2, heading `<h4 id="s2-h">`
Evidence: `<h2 id="s1-h">Fare adjustments</h2>` followed later by `<h4 id="s2-h">Accessibility improvements</h4>`
Problem: The heading level jumps from h2 to h4, skipping h3 and breaking the document's heading hierarchy.
Fix: Change `s2-h` to `<h2>` (or add the missing h3 level consistently) to keep headings sequential.

Location: section s2, heading and body

Location: `<table id="s2-table1">`

Location: `<p id="s3-linkpara">`

Location: s3-form, phone field
Evidence: `<label for="phone" id="s3-form-phone-label">Phone number (required)</label>` with `<input id="phone" type="tel">`
Problem: The label text tells users the field is required, but the input has no `required` or `aria-required="true"` attribute, so this isn't enforced or exposed to assistive technology.
Fix: Add `required` (and/or `aria-required="true"`) to the `phone` input.

Location: s3-form, promo field
Evidence: `<input id="promo" type="text" aria-invalid="true">`
Problem: `aria-invalid="true"` is hardcoded on page load before the user has entered anything, incorrectly announcing an error state prematurely.
Fix: Set `aria-invalid="false"` (or omit it) by default and only set it to `true` after validation fails.

Location: s3-form, promo error text
Evidence: `<input id="promo" type="text" aria-invalid="true">` followed by `<span class="error-text" id="s3-form-promo-error">Enter a 6 character code...</span>`
Problem: The error message is not programmatically associated with the input (no `aria-describedby`), so screen reader users won't hear it when focusing the field.
Fix: Add `aria-describedby="s3-form-promo-error"` to the `promo` input.

Location: s3-form submit button
Evidence: `<button type="submit" class="btn-primary" id="s3-form-submit" aria-label="Send form now">Submit</button>`
Problem: The `aria-label` ("Send form now") does not contain the visible text ("Submit"), violating the WCAG "Label in Name" requirement and causing a mismatch for speech-input and screen reader users.
Fix: Remove the `aria-label` or change it to include the visible text, e.g. `aria-label="Submit form"`.
