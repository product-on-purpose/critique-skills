Location: `<html lang="translanguage">`
Evidence: `lang="translanguage"`
Problem: "translanguage" is not a valid BCP 47 language code, so assistive technology and browsers cannot determine the page's language.
Fix: Set `lang` to the actual content language, e.g. `lang="en"`.

Location: `<title id="head-title"></title>` in `<head>`
Evidence: `<title id="head-title"></title>`
Problem: The page title is empty, so the browser tab, history, bookmarks, and screen readers have no identifying title for this page.
Fix: Add descriptive text, e.g. `<title>Rider service updates</title>`.

Location: Section `s1`, paragraphs `s1-p1` and `s1-p2`
Evidence: Both end with "Station staff can also help with the same request in person."
Problem: The identical trailing sentence is reused verbatim for two unrelated actions (requesting a fare adjustment vs. checking arrivals); checking real-time arrivals isn't a "request" staff process in person, so the second instance doesn't make sense.
Fix: Write a sentence specific to each paragraph's actual action, or remove the ill-fitting reuse in `s1-p2`.

Location: `<img src="/img/platform-update.jpg" id="s1-img1">`
Evidence: `<img src="/img/platform-update.jpg" id="s1-img1">`
Problem: The image has no `alt` attribute, so screen reader users get no description of its content.
Fix: Add an `alt` attribute describing the image, or `alt=""` if it is purely decorative.

Location: Custom control `s3-customcontrol`
Evidence: `<div class="icon-delete" role="button" tabindex="0" aria-label="Delete item" id="s3-customcontrol">`
Problem: A non-semantic `<div>` is used to fake a button instead of a native `<button>` element, and it has no associated item for it to delete — it is disconnected from any list or record on the page.
Fix: Replace with a native `<button>` element, and either attach it to a specific item or remove it if it has no functional context on this page.

Location: Link `s3-link1`
Evidence: `<a href="/fares/history" id="s3-link1">click here</a>`
Problem: "click here" is non-descriptive link text, which fails accessibility guidance (link purpose should be clear out of context) and hurts SEO.

Location: Form field `phone`
Evidence: `<label for="phone" id="s3-form-phone-label">Phone number (required)</label>` next to `<input id="phone" type="tel">`
Problem: The label text claims the field is required, but the input has no `required` or `aria-required="true"` attribute, so assistive technology and form validation won't actually enforce or announce it as required.
Fix: Add `required` (or `aria-required="true"`) to the `phone` input.

Location: Form field `promo`
Evidence: `<input id="promo" type="text" aria-invalid="true">` with `<span class="error-text" id="s3-form-promo-error">Enter a 6 character code...</span>`
Problem: `aria-invalid="true"` is hardcoded regardless of actual input state, and the error text is not programmatically associated with the input via `aria-describedby`, so screen reader users won't reliably hear the error reason.
Fix: Set `aria-invalid` dynamically based on validation state, and add `aria-describedby="s3-form-promo-error"` to the `promo` input.

Location: Submit button `s3-form-submit`
Evidence: `<button type="submit" class="btn-primary" id="s3-form-submit" aria-label="Send form now">Submit</button>`
Problem: The accessible name ("Send form now") does not contain the visible label text ("Submit"), violating the WCAG "Label in Name" requirement and confusing voice-control/screen-reader users who reference the visible text.
Fix: Remove the `aria-label` or change it to include the visible text, e.g. `aria-label="Submit form"`.
