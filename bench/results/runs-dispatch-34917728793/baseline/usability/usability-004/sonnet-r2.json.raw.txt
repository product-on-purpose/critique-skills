Location: `<head>` element
Evidence: `<meta charset="utf-8">` is the only meta tag present; no `<meta name="viewport" ...>` is included
Problem: Without a viewport meta tag, this workspace UI mockup will render at desktop scale on mobile browsers, defeating the purpose of a UI mockup meant to be viewed/tested across devices.
Fix: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` to the head.

Location: `#workspace-overview`, intro paragraph and list
Evidence: "This workspace holds 4 projects, synced last week." followed by a `<ul>` with only three `<li>` entries (Holiday Campaign Assets, Support Backlog Triage, Mobile App Revamp)
Problem: The stated project count (4) doesn't match the number of projects actually listed (3), an internal inconsistency.
Fix: Either add the missing fourth project to the list or correct the count in the paragraph to 3.

Location: `#workspace-overview-recent` div
Evidence: `<div id="workspace-overview-recent">` sits directly under the "Your projects" heading with no label indicating it's a partial/recent subset, despite the div's own id containing "recent"
Problem: A reader has no way to tell whether this list is meant to be the complete project list or just a "recent" subset, since no heading or caption communicates that distinction.
Fix: Add a visible heading (e.g., "Recent projects") above the list, or rename the div if it is meant to be the full list.

Location: `#project-settings`, duplicate button
Evidence: `<button id="project-settings-duplicate-btn" type="button" aria-label="Duplicate project"></button>`
Problem: The button has no visible text content or icon, so sighted users have no indication of its purpose or even that it's a distinct control — only screen reader users get the aria-label.
Fix: Add visible text (e.g., "Duplicate") or an icon with the aria-label retained for accessibility.

Location: `#project-settings-name-input`, `#invite-member-email-input`, `#notification-settings-digest-input`
Evidence: `<input id="project-settings-name-input" type="text" value="Q3 Roadmap">`, `<input id="invite-member-email-input" type="email">`, `<select id="notification-settings-digest-input">` — none have a `name` attribute
Problem: Without `name` attributes, these fields would not be included in form submission data if this mockup were wired to a real backend.
Fix: Add appropriate `name` attributes to each form control.

Location: `#invite-member` section
Evidence: The form has a `<button id="invite-member-save-btn" type="submit">Save</button>` and, separately, `<a id="invite-member-continue-link" href="#invite-sent">Continue</a>`
Problem: It's unclear whether clicking "Save" or "Continue" is what actually sends the invite; having both a submit button and a separate forward-navigation link for the same form creates ambiguous, overlapping affordances.
Fix: Remove the redundant control — e.g., have the Save button itself navigate to `#invite-sent` on success, and drop the separate Continue link.

Location: `#archive-confirm`, `archive-confirm-copy` paragraph
Evidence: "You can restore it at any time from the archived projects list."
Problem: The mockup has no page, section, or link anywhere for an "archived projects list," so this refers to a destination that doesn't exist in the document.
Fix: Either add an archived-projects-list section/link or remove the reference to restoring from it.

Location: `#project-settings-save-btn` and `#notification-settings-save-btn`
Evidence: Both are `type="submit"` buttons inside forms with no `action` attribute and no associated confirmation section or forward link, unlike the invite flow (`#invite-sent`) and archive flow (`#project-archived`) which both lead to explicit confirmation screens
Problem: Saving project settings or notification settings has no defined outcome or user feedback in the mockup, inconsistent with the confirmation pattern used elsewhere for state-changing actions.
Fix: Add a confirmation state/section (or at least a success message) reached after saving, matching the pattern used for invites and archiving.
