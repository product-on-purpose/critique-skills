Location: <html> element, lang attribute, near the top of the document
Evidence: <html lang="translanguage" id="html">
Problem: The lang attribute value "translanguage" is not a valid language code, so browsers and screen readers cannot correctly determine what language the page content is in.
Fix: Set lang to the actual language of the page content, for example lang="en".

Location: <head>, the <title> element
Evidence: <title id="head-title"></title>
Problem: The page title is empty, so the browser tab, bookmarks, browser history, and screen reader users all have no name for this page.
Fix: Add descriptive text inside the title element, such as "Rider service updates".

Location: section id="s1", the two paragraphs id="s1-p1" and id="s1-p2"
Evidence: Both paragraphs end with the identical sentence "Station staff can also help with the same request in person."
Problem: The same closing sentence is reused for two different topics, requesting a fare adjustment and checking real time arrivals, which reads as a copy-paste error rather than text written for the second paragraph.
Fix: Write a sentence specific to checking real time arrivals, or remove the reused line if it does not apply there.

Location: section id="s1", image id="s1-img1"
Evidence: <img src="/img/platform-update.jpg" id="s1-img1">
Problem: The image has no alt attribute at all, so its content or purpose is unavailable to anyone using a screen reader or with images turned off.
Fix: Add an alt attribute describing what the image shows, or alt="" if it is purely decorative.

Location: section id="s2", heading id="s2-h"
Evidence: <h4 id="s2-h">Accessibility improvements</h4> appears at the same nesting level as the h2 headings in section id="s1" and section id="s3"
Problem: The heading level jumps from h2 straight to h4, skipping h3, which breaks the document's logical heading hierarchy and can confuse anyone navigating by headings.
Fix: Change the heading to h2, to match its sibling section headings, or to h3 if it is meant to be a subsection of something else.

Location: section id="s2", table id="s2-table1"
Evidence: <table id="s2-table1"><tr><th scope="col">Zone</th><th scope="col">Status</th></tr>...
Problem: The table has no caption or other accessible name, so someone landing on the table with a screen reader has no description of what data it holds.
Fix: Add a caption element inside the table, for example "Zone status".

Location: paragraph id="s2-p1" and paragraph id="s3-p2"
Evidence: Both contain the sentence "Updates post to the schedule page within one business day."
Problem: The same sentence is reused verbatim for reporting a service issue and for reviewing the schedule through the online portal, so it reads as boilerplate that was not adapted to the second paragraph's actual topic.
Fix: Replace the reused sentence in one of the two paragraphs with wording relevant to its own topic, or remove it where it does not apply.

Location: paragraph id="s3-p1" and div id="s3-statuscard"
Evidence: Both contain the sentence "A confirmation message follows once the request is processed."
Problem: This sentence is reused for reporting a service issue and for checking real time arrivals, but checking arrivals does not produce a request that gets processed, so the sentence does not fit its second context.
Fix: Remove or rewrite the sentence inside the status card to describe what actually happens when a rider checks real time arrivals.

Location: section id="s3", div id="s3-customcontrol"
Evidence: <div class="icon-delete" role="button" tabindex="0" aria-label="Delete item" id="s3-customcontrol"><img src="/img/trash-icon.svg" alt=""></div>
Problem: A div with role="button" and tabindex="0" is used to simulate a button instead of a native button element, and the aria-label "Delete item" does not say which item would be deleted.
Fix: Replace the div with a native button element, and make the label specific to the item it deletes, for example "Delete route from favorites".

Location: section id="s3", div id="s3-wizard" and its step divs id="s3-step1", id="s3-step2", id="s3-step3"
Evidence: "Choose a plan", "Enter payment details", "Confirm your order"
Problem: These three steps describe a purchase or checkout flow, but they appear inside a section titled "Station updates" whose surrounding content is about fares, schedules, and arrivals, so the wizard reads as unrelated to the rest of the section.
Fix: Move the wizard to the page or section it actually belongs to, or add surrounding text explaining what plan and payment it refers to.

Location: paragraph id="s3-linkpara", link id="s3-link1"
Evidence: <a href="/fares/history" id="s3-link1">click here</a>
Problem: The link text "click here" does not describe where the link goes, so it is meaningless when read out of context, such as in a list of links generated by a screen reader.
Fix: Change the link text to something descriptive, such as "full list of upcoming adjustments".

Location: form id="s3-form", label id="s3-form-phone-label" and input id="phone"
Evidence: Label text reads "Phone number (required)" but <input id="phone" type="tel"> carries no required or aria-required attribute.
Problem: The label tells the user the field is required, but the input itself is not marked required, so form validation and assistive technology will not actually treat it as mandatory.
Fix: Add the required attribute, or aria-required="true", to the phone input.

Location: form id="s3-form", label id="s3-form-email-label" and input id="email"
Evidence: <label for="email" id="s3-form-email-label">Email address</label> followed by <input id="email" type="email"> with no required or optional indication
Problem: Unlike the phone field, the email label does not state whether the field is required or optional, leaving the user unable to tell whether it must be filled in before submitting.
Fix: Add "(required)" or "(optional)" to the email label, matching the pattern already used for the phone field.

Location: form id="s3-form", input id="promo"
Evidence: <input id="promo" type="text" aria-invalid="true">
Problem: The promo code input is marked aria-invalid="true" in the page's initial markup, before the user has entered or submitted anything, so it will be announced as invalid on first load.
Fix: Remove aria-invalid from the initial markup, or set it to "false", and only switch it to "true" after the user submits an invalid value.

Location: form id="s3-form", input id="promo" and span id="s3-form-promo-error"
Evidence: <input id="promo" type="text" aria-invalid="true"><span class="error-text" id="s3-form-promo-error">Enter a 6 character code using letters and numbers only.</span>
Problem: The error text is not associated with the promo input through any attribute such as aria-describedby, so a screen reader user focused on the field will not hear the error message.
Fix: Add aria-describedby="s3-form-promo-error" to the promo input.

Location: form id="s3-form", submit button id="s3-form-submit"
Evidence: <button type="submit" class="btn-primary" id="s3-form-submit" aria-label="Send form now">Submit</button>
Problem: The aria-label "Send form now" replaces the visible text "Submit" as the button's accessible name, so the name announced to screen reader users does not match the text sighted users see printed on the button.
Fix: Remove the aria-label so the accessible name comes from the visible text, or change the aria-label to match it exactly.
