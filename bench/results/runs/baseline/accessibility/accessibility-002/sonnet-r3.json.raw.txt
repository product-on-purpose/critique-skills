Location: the viewport meta tag in the head
Evidence: content="width=device-width, initial-scale=1, user-scalable=no"
Problem: user-scalable=no disables pinch to zoom, which stops anyone who needs to zoom in from doing so.
Fix: Remove user-scalable=no (and any maximum-scale restriction) from the viewport content string.

Location: the "Accessibility improvements" section, its heading and the two paragraphs under it
Evidence: heading text "Accessibility improvements" followed by "Passengers should review the updated schedule at any station kiosk." and "Local residents may request a fare adjustment through the mobile app."
Problem: Neither paragraph under this heading is actually about accessibility; both are about checking schedules and requesting fare adjustments, so the heading misrepresents the section's content.
Fix: Rename the heading to match the schedule and fare content, or replace the paragraph text with information about actual accessibility improvements.

Location: first paragraph of the "Accessibility improvements" section
Evidence: style="color:#999999"
Problem: Light gray text on what appears to be a white page background is low contrast and hard to read.
Fix: Darken the text color, for example to #595959 or the same color used for the surrounding body text.

Location: first and second paragraphs of the "Accessibility improvements" section, and the status card paragraph later in the "Weekend service" section
Evidence: "Updates post to the schedule page within one business day." appears in both paragraphs of the first section and again, nearly word for word, in the status card paragraph
Problem: The same boilerplate sentence is repeated three times across otherwise unrelated paragraphs, which makes the content feel templated and buries whatever is distinct about each paragraph.
Fix: Remove the repeated sentence from all but the one place it is actually relevant, or reword each paragraph so it says something new.

Location: the image in the "Accessibility improvements" section
Evidence: alt="A transit operator inspecting the platform screen doors before the morning shift."
Problem: The alt text describes a scene that has nothing to do with the surrounding paragraphs about schedule kiosks and fare adjustments, so it does not explain why the image is there.
Fix: Rewrite the alt text to describe what the image actually illustrates in this section, or remove the image if it does not belong here.

Location: the sentence just before the form in the "Weekend service" section
Evidence: link text "read the accessibility improvements list" pointing to href="/fares/history"
Problem: The link text promises an accessibility improvements list but the destination is a fare history page, so a reader who follows it lands somewhere unrelated to what was promised.
Fix: Change the link text to describe the fare history page it goes to, or point the link at an actual accessibility improvements page.

Location: the promo banner in the "Weekend service" section
Evidence: style="width:960px"
Problem: A hardcoded 960 pixel width will overflow narrow screens, and because the page also disables zooming, a mobile reader has no way to see or reach the rest of the banner.
Fix: Replace the fixed pixel width with a relative unit such as max-width:100% so the banner adapts to the viewport.

Location: the status card in the "Weekend service" section
Evidence: style="height:60px;overflow:hidden" wrapping the paragraph "Riders can report a service issue through the online portal. Updates post to the schedule page within one business day."
Problem: A fixed 60 pixel height combined with overflow:hidden will silently cut off the paragraph text whenever it does not fit, with no scrollbar or other sign that content is missing.
Fix: Let the card grow to fit its content instead of clipping it, for example by dropping the fixed height or switching to min-height with visible overflow.

Location: the delete icon control in the "Weekend service" section
Evidence: role="button" tabindex="0" aria-label="Delete item" wrapping an image with empty alt text
Problem: The control is labeled "Delete item" but nothing nearby in the weekend service section indicates what item it deletes, so its purpose is unclear to anyone reading the page.
Fix: Move the control next to the item it acts on and give it a label naming that item, or remove it if it serves no purpose on this page.

Location: the wizard steps block in the "Weekend service" section
Evidence: three plain divs with class "step" reading "Choose a plan", "Enter payment details", and "Confirm your order", with no indication of which step is current
Problem: A sequence of steps is presented as unstructured divs with no list markup and no way to tell which step the user is currently on.
Fix: Mark the steps up as an ordered list and indicate the current step, for example with an aria-current attribute.

Location: the Route field in the weekend service form
Evidence: label for="topic-alt" reading "Route" immediately followed by a select with id="topic"
Problem: The label's for attribute references topic-alt, which does not match the select's id of topic, so the label is not actually associated with the field and clicking or reading the label will not reach it.
Fix: Change the label's for attribute to topic so it matches the select element's id.

Location: the phone number field in the weekend service form
Evidence: label text "Phone number (required)" followed by input id="phone" type="tel" with no required or aria-required attribute
Problem: The label tells the reader the phone field is required, but the input itself carries no required or aria-required attribute, so that requirement is never enforced or exposed to assistive technology.
Fix: Add required or aria-required="true" to the phone input so its actual required state matches what the label says.

Location: the promo code field in the weekend service form
Evidence: input id="promo" type="text" aria-invalid="true" followed by a separate span id="s3-form-promo-error" holding the error text, with no attribute linking the two
Problem: The promo field is marked invalid but has no aria-describedby pointing at its error message, so a screen reader user focused on the field is never told what the error is.
Fix: Add aria-describedby="s3-form-promo-error" to the promo input.
