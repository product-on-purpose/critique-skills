Location: Signup form, email field — first message entry, Message field
Evidence: "The connection dropped before this finished."
Problem: The pronoun "this" has no clear antecedent, so the user can't tell what action failed (the page load, the submission, a validation check) or what to retry.
Fix: Name the action explicitly, e.g. "The connection dropped before your sign-up could be sent."

Location: Signup form, email field — first message entry, Fires field
Evidence: "Fires: on-blur" paired with "The connection dropped before this finished."
Problem: A dropped-connection error implies a network call was in flight, but on-blur fires from simply leaving the field with no network call involved, so the stated trigger can't actually produce this failure.
Fix: Change Fires to on-submit (or whichever event actually initiates the network request this message refers to).

Location: Signup form, email field — first message entry, Predictable mistake field
Evidence: "Predictable mistake: yes" on "The connection dropped before this finished."
Problem: A dropped connection is a system/infrastructure failure, not a user mistake, so classifying it as a predictable mistake is inconsistent with the parallel checkout entry "Something went wrong..." which is marked "no" for the same kind of system-level failure.
Fix: Change to "Predictable mistake: no" to match the equivalent system-failure entry.

Location: Signup form, email field — second message entry, Signal field
Evidence: "Signal: one step bolder and larger than the field label, none"
Problem: This is the only entry in the document with no icon, relying solely on a one-step increase in weight/size to signal an error — a weaker, less accessible signal than every other entry uses, for what is likely the first validation error a new user ever sees.
Fix: Add an icon (or color cue) consistent with the other entries so the error isn't communicated through text weight/size alone.

Problem: The placement explicitly describes a banner, but the Container field labels it "inline," which directly contradicts the placement description.

Location: Checkout form, payment method — second message entry, Fires field
Evidence: "Fires: mid-keystroke" on "The expiry date on this card has passed."
Problem: Whether an expiry date has passed can't be determined until both month and year are fully entered, so firing mid-keystroke will flag the card as expired while the user is still typing a valid date.
Fix: Change Fires to on-blur (or trigger only once month and year are both complete).

Evidence: "You keep entering the wrong value. Re-enter it to continue." / Suggested fix: none
