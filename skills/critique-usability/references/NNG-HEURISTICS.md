# NNG-HEURISTICS: Nielsen's 10 usability heuristics (paraphrased)

The criterion registry for the `NNG-H*` namespace: every criterion `critique-usability` declares in
`SKILL.md`'s `checks.scripted` or `checks.judged` has exactly one row in the table below.

Every operationalization here is this skill's own original wording, written against this skill's
artifact claim, with the source cited by `rubric_sources.id` rather than reproduced
([ADR 0006 (copyright and paraphrase policy)](../../../docs/internal/decisions/0006-copyright-paraphrase-policy.md)).

## Source citation

- **Living reference (canonical URL):** Nielsen, J. (originally published 1994-04-24, last
  updated 2024-01-30). 10 Usability Heuristics for User Interface Design. Nielsen Norman Group.
  `https://www.nngroup.com/articles/ten-usability-heuristics/` Accessed 2026-07-31.
- **Original academic source (ISBN + page range):** Nielsen, J. (1994). Heuristic Evaluation. In
  Nielsen, J., and Mack, R. L. (Eds.), *Usability Inspection Methods*, pp. 25-62. New York: John
  Wiley & Sons. ISBN 0-471-01877-5.
- `rubric_sources.operationalization`: `paraphrased` (copyrighted NN/g material).

## Artifact claim

Everything below is evaluated against **HTML or markdown UI specs and page mockups, not live running
applications** ([S-05 (skills slate)](../../../docs/internal/release-plans/plan_v0.1.0/S-05_skills-slate/spec.md)
AC-8). Where a heuristic leans on runtime behavior, the criterion asks what the artifact commits to:
whether the spec defines a status indication, an exit, a confirmation, a label. It never asks how the
running product behaves, because a static artifact cannot evidence that.

## Source anchors

Short anchor quotes of the ten heuristic titles, given once so a reader can map an ID back to its
source item. The criterion text itself is paraphrase, never these strings.

- `NNG-H1` covers heuristic 1, "Visibility of system status".
- `NNG-H2-*` cover heuristic 2, "Match between the system and the real world".
- `NNG-H3-*` cover heuristic 3, "User control and freedom".
- `NNG-H4-*` cover heuristic 4, "Consistency and standards".
- `NNG-H5-*` cover heuristic 5, "Error prevention".
- `NNG-H6-*` cover heuristic 6, "Recognition rather than recall".
- `NNG-H7-*` cover heuristic 7, "Flexibility and efficiency of use".
- `NNG-H8` covers heuristic 8, "Aesthetic and minimalist design".
- `NNG-H9-*` cover heuristic 9, "Help users recognize, diagnose, and recover from errors".
- `NNG-H10-*` cover heuristic 10, "Help and documentation".

## Registry

20 criteria across exactly the 10 heuristics. Seven heuristics carry sub-criteria because the
heuristic names two or more independently checkable behaviors (criterion-ids permanence rule 4, one
criterion one ID); H1 and H8 stay single. Three sub-criteria are the scripted lane, per
[ADR 0021 (usability lane split)](../../../docs/internal/decisions/0021-usability-lane-split-structural-floor-plus-judged-criterion.md).
Sub-criteria use a descriptive suffix rather than a numeric dot part, because dot notation is reserved
for preserving an upstream numbering scheme verbatim and Nielsen publishes no sub-numbering
([criterion-ids.md](../../../docs/reference/criterion-ids.md)).

Rows are in this skill's canonical sweep order: heuristic number ascending, then suffix alphabetical.

| ID | Operationalization | Operational test | Severity 2 anchor | Severity 3 anchor | Lane | Lane rationale |
|---|---|---|---|---|---|---|
| NNG-H1 | For every action or process the artifact describes that changes state or takes time, the artifact specifies a visible indication of what the system is doing and what the outcome was, placed where the user is already looking (NNG-HEURISTICS, heuristic 1). | For each state-changing or long-running action the artifact names (submit, upload, save, delete, sync, search), check whether the artifact also names what the user sees while it runs and once it finishes: a loading state, a progress element, a success or failure message, or a changed control state. Flag an action whose trigger is specified but whose in-progress and result feedback are not. Do not flag an action whose result is arriving on a next screen that the artifact itself defines. | A settings page commits a preference toggle immediately and specifies no confirmation of the save; the toggle's own new position still shows the user what happened, so the missing message costs reassurance rather than comprehension. | A multi-minute import flow specifies an import trigger and a finished screen with nothing between them, so a user cannot tell whether the import is running, stalled, or already failed, and the uncertainty lasts for the whole operation. | judged | Deciding which actions need feedback at all, and whether what the artifact specifies is unambiguous, requires reading the flow as a whole rather than matching a pattern. |
| NNG-H2-CONVENTIONS | The artifact orders, groups, and names things the way the underlying real-world task is actually performed, or the way comparable interfaces the user already knows do, rather than mirroring the system's internal processing order (NNG-HEURISTICS, heuristic 2). | For each multi-step flow or grouped screen region, restate the real-world task it stands for, then compare the artifact's step order and grouping against it. Flag an order or grouping that only makes sense from the system's side: asking for payment before the user has chosen what to buy, grouping form fields by storage table rather than by the moment the user knows the answer, or naming a step after the process that consumes it. | A form asks for a shipping address before showing what is in the cart, reordering two steps the user can still complete in either order without losing anything. | A booking flow asks the user to confirm and pay before it ever displays the date and time being booked, inverting the real-world decide-then-commit order so the user commits money before seeing what they bought. | judged | Requires modelling the real-world task the artifact stands for; there is no fixed pattern that identifies a wrong order. |
| NNG-H2-LANGUAGE | Labels, prompts, headings, and body text in the artifact use the words the stated target user already has for the task, rather than internal engineering, storage, or business-process vocabulary (NNG-HEURISTICS, heuristic 2). | Collect every user-facing string in the artifact. Flag a string that names an internal system concept (a storage table, an internal status value, an org-chart term, a service or API noun) where the user's own task vocabulary has a word for the same thing and the artifact offers no in-place explanation. Judge against the audience the artifact names; where it names none, judge against a first-time user of this product category. | One filter control on a report screen is labeled with an internal status value while every other control on the page uses task language, and the filter's effect is visible immediately after use. | The primary navigation of a customer-facing dashboard is labeled entirely in internal service names, so a user cannot even guess where a task lives, and the guessing cost is paid again on every visit. | judged | Deciding that a term is jargon for this artifact's audience requires knowing who that audience is and what they already know, which no fixed word list settles. |
| NNG-H3-DEADEND | Every state the artifact defines offers at least one control leading to another state the artifact also defines, so the artifact contains no screen a user can reach and then not leave (NNG-HEURISTICS, heuristic 3). | Build the state graph from the artifact: nodes are the screens or states it defines, edges are the controls or links whose target names another defined state. Flag any defined state with zero outgoing edges. An edge whose named target is defined nowhere in the artifact does not count as an outgoing edge, so a state whose only exit points at an undefined target is reported as a dead end. | A terminal confirmation state that nothing else in the artifact links into has no onward control, so the defect sits in a fragment of the spec no user path reaches. | An error state reachable from the middle of a checkout flow defines no back, retry, or cancel control, so a user who lands there has no path in the artifact back to their cart. | scripted | Purely structural: the check counts outgoing edges in the artifact's own link graph and makes no judgment about whether an exit is a good one. |
| NNG-H3-EXIT | A user who enters a flow by mistake can leave by an exit that is visible where they are looking, labeled so its effect is predictable, and costs them nothing they have already entered before anything commits (NNG-HEURISTICS, heuristic 3). | For each multi-step or modal flow, find the exit the artifact provides and check three things: it is on the screen rather than assumed from browser navigation, its label predicts what it does, and the artifact says what becomes of work already entered. Flag a flow whose exit is hidden, ambiguously labeled, or silently discards entered work. Do not re-report a flow already flagged under NNG-H3-DEADEND, which covers the case of no exit at all. | A modal's only dismissal is an unlabeled corner control, on a flow that holds no user-entered data, so the ambiguity costs a moment of hesitation and nothing else. | A five-step onboarding wizard shows no cancel or skip control on any step, so a user who opened it by accident can only escape by abandoning the page, and the artifact never says what happens to the account created on step one. | judged | Whether an exit is obvious and low-cost is a reading of the whole screen and the user's investment in it, not a property a script can measure. |
| NNG-H3-UNDO | An action the artifact treats as committed but which is reasonably reversible in the product it describes offers a stated way back, such as undo, restore, or edit, rather than leaving the outcome permanent by default (NNG-HEURISTICS, heuristic 3). | List every action in the artifact that changes stored state (delete, archive, send, publish, apply, assign). For each, check whether the artifact names a reversal path and where the user finds it. Flag an action that is reasonably reversible in this product but whose reversal appears nowhere in the artifact. An action that genuinely cannot be reversed is out of scope here and is evaluated under NNG-H5-CONFIRM instead. | A bulk tag-assignment action names no undo, though the artifact shows each tag can be removed individually afterwards, so recovery exists and costs one step per item. | A publish action makes a draft public immediately with no unpublish or revert named anywhere in the artifact, so an accidental publish has no path back in the design as specified. | judged | Requires deciding whether an action is reasonably reversible in this product, a judgment about the domain rather than about the text. |
| NNG-H4-CONTROL-NAMING | The artifact names one recurring interaction with one label throughout, rather than alternating between interchangeable synonyms for the same commit, cancel, or back action (NNG-HEURISTICS, heuristic 4). | Extract every control label in the artifact: button text, link text, and menu item text. Compare them against the fixed synonym sets held in scripts/checks.py, one per recurring action class (commit, cancel, back). Flag the artifact once per synonym set in which two or more distinct members appear, listing every occurrence as instances. Comparison is case-insensitive and ignores surrounding punctuation and trailing ellipsis. The claim this criterion makes is exactly that: two interchangeable labels for one action class appear in one artifact. It does not establish that the two controls perform the same operation, which a script cannot see, so an artifact that deliberately distinguishes two actions by these labels clears the criterion by saying so in place, and the reviewer dispositions the finding rather than the criterion changing lane. | A settings area labels its commit control Save on one tab and Apply changes on another, both reachable from the same navigation, so the user has to work out whether the two do the same thing. | One multi-step flow uses three different commit synonyms on consecutive steps of a single task, so at no step can the user tell whether they are storing a draft or committing the whole flow. | scripted | A membership test over fixed synonym sets and the artifact's own control labels; the same artifact yields the same set of matches on every run and any machine. |
| NNG-H4-EXTERNAL | Controls, icons, placement, and wording follow the settled conventions of the platform or product category the artifact belongs to, so a user's existing habits transfer instead of having to be unlearned (NNG-HEURISTICS, heuristic 4). | Identify the artifact's platform or category from what it states or from the chrome it shows. For each convention-bearing element (primary action placement, destructive-action styling, icon meanings, form-control types, navigation position), compare it against that platform's settled convention. Flag an element that inverts or reassigns a convention. Do not flag a departure the artifact justifies and signposts in place. Where the artifact names no platform and shows no platform chrome, report nothing under this criterion: an unstated platform is not evidence of a breach, and picking one in order to have a convention to measure against is the reviewer supplying the finding. | A dialog puts its primary action on the left and its cancel on the right, the reverse of the platform convention, on a dialog whose actions are both non-destructive. | A magnifying-glass icon in the toolbar opens a zoom control rather than search, so the strongest habit a user brings from every other product leads them to the wrong feature every time they need to find something. | judged | Requires knowing the conventions of the platform and deciding that this artifact belongs to it, neither of which is derivable from the file alone. |
| NNG-H4-INTERNAL | Within the artifact, one word, icon, or interaction pattern stands for exactly one thing, and one thing is named the same way everywhere it appears, beyond the control-label synonyms NNG-H4-CONTROL-NAMING already matches (NNG-HEURISTICS, heuristic 4). | Build a term-to-meaning map from the artifact: every domain noun, icon, and repeated interaction pattern, with the meaning it carries in each place it appears. Flag a term or icon carrying two meanings, and flag two terms carrying one meaning, wherever the artifact gives the reader no cue that they differ or coincide. Do not re-report a control-label pair already flagged by NNG-H4-CONTROL-NAMING. | One domain noun names a billing container on the account screen and a workspace folder in the sidebar, with enough surrounding context that a reader can still tell the two apart. | A trash icon means delete permanently in the file list and remove from this view in the sidebar, so one icon carries a recoverable and an unrecoverable meaning inside a single artifact. | judged | Requires reading meaning in context across the whole artifact, which is the definition of a judgment call. |
| NNG-H5-CONFIRM | An action whose consequence is costly or cannot be undone is gated behind an explicit confirmation that names what is about to happen, rather than firing on a single click (NNG-HEURISTICS, heuristic 5). | List every destructive or costly action the artifact defines (delete, remove, cancel a subscription, send to recipients, overwrite, pay). For each, follow the path the artifact gives that control: the target its link or button names, or the next step a markdown spec assigns it. Check that the path reaches a confirmation before the action commits, and that the confirmation wording names the object and the consequence. A confirmation state the artifact defines but that this control's own path bypasses does not count, because a user taking that control never sees it. Flag an action whose path reaches neither a confirmation nor an undo, and flag a confirmation whose wording never says what will be lost. | A remove-collaborator action confirms with a generic prompt that does not name the collaborator, on an action the artifact shows can be reversed by re-inviting. | A delete-workspace control fires on one click with no confirmation and no undo named anywhere in the artifact, so a single mis-click destroys every document in the workspace. | judged | Requires judging how costly an action is in this product before deciding whether the gating the artifact specifies is adequate. |
| NNG-H5-PREVENT | The design makes the likely error impossible or unlikely before it happens, by constraining what can be entered or selected and in what order, rather than relying on an error message afterwards (NNG-HEURISTICS, heuristic 5). | For each input, selection, or step ordering the artifact defines, name the most likely wrong entry and check whether the design admits it. Flag an input that accepts a value the system will later reject where a constrained control would have prevented it: a picker, a bounded list, a disabled-until-valid state, a sensible default, or format assistance. Flag an ordering that lets the user complete steps in a sequence the system cannot honor. | A free-text country field accepts any string where the artifact elsewhere shows a fixed country list, so a mistyped entry is caught at submission rather than at entry. | A scheduling screen accepts an end time earlier than its start time and surfaces the conflict only after the booking is sent and rejected, so users routinely lose a whole form to a mistake the control could have ruled out. | judged | Requires reasoning about what a user is likely to get wrong here and whether a different control would have prevented it. |
| NNG-H6-LABELED | Every interactive control and every input the artifact defines carries a name the user can read on screen, so nothing has to be identified by memory, position, or trial (NNG-HEURISTICS, heuristic 6). | Collect every control the artifact defines: in HTML, the interactive elements and form inputs; in a markdown spec, the entries of its control or field lists. Flag a control with no readable name: an element with neither text content nor an accessible-name attribute, an input with no associated label element, or a spec list entry that names a control by role alone. Report one finding per unnamed control, grouped as instances where the same control repeats. | One icon-only button sits in a toolbar of otherwise labeled controls with no text and no title attribute, and its labeled neighbours give a partial cue to its purpose. | A form's inputs carry no label elements at all, only placeholder text, so once the user starts typing there is nothing on screen naming what any field holds. | scripted | The presence of a name on a control is a structural property of the markup or of the artifact's own control list; no judgment is needed to see that a name is absent. |
| NNG-H6-RECALL | The information a user needs at a given step is present at that step, rather than held over from an earlier screen or expected to be remembered (NNG-HEURISTICS, heuristic 6). | Walk each flow the artifact defines step by step, listing what the user must know at each step in order to act. Flag a step that needs a value, a rule, or an option shown only on an earlier screen and neither repeated, referenced, nor retrievable in place. Flag an option available only to a user who already knows to ask for it, with no visible equivalent. | A confirmation step shows an order total but not the shipping address entered two steps earlier, which the user can still verify by going back without losing input. | A transfer form requires an account number the artifact displays only on a different screen behind separate navigation, so the user must leave the flow and memorize a long string to finish it. | judged | Requires simulating the user's knowledge state across a flow, which no single-file pattern match can do. |
| NNG-H7-ACCELERATORS | The artifact provides a faster route through a task it treats as frequent, such as a shortcut, a bulk action, or a saved default, while the step-by-step route stays available to a first-time user (NNG-HEURISTICS, heuristic 7). | Identify the tasks the artifact itself treats as frequent, whether by repeating them in a flow, listing them as primary, or saying so. For each, check whether any faster path exists and whether that path is additive rather than a replacement for the discoverable one. Flag a frequent task offering only the long route, and flag a shortcut that has become the only route. | A list screen supports selecting items but offers no bulk action for the one operation its own copy calls routine, so the user repeats a two-click operation per row. | A triage screen the artifact describes as used continuously offers no keyboard path and no bulk action anywhere, so its heaviest users click through five controls per item for an entire session. | judged | Requires deciding which tasks are frequent for this artifact's users before an accelerator can be called missing. |
| NNG-H7-CUSTOMIZE | Where the artifact shows a user making the same choice repeatedly, the design lets that choice be remembered, defaulted, or tailored rather than re-entered every time (NNG-HEURISTICS, heuristic 7). | Find every place the artifact itself shows the same input, filter, or configuration being asked for more than once: twice in one flow, on two screens the artifact places on one user's path, or on a screen the artifact says is returned to repeatedly. Flag one where nothing in the artifact carries the previous answer forward: no default, no recent list, no saved view, no per-user setting. Do not flag a repeated choice the artifact deliberately re-asks for safety reasons it states, and do not infer repetition the artifact does not show. | A report screen resets its date range to the default on every visit, so a user watching one period reselects it each time from a control that takes two clicks. | A daily data-entry screen re-asks the same five context fields on every record, with no defaults and no copy-from-previous, so the routine path through the artifact is dominated by re-entering unchanged values. | judged | Requires recognizing that two prompts are the same choice for the same user, which depends on task meaning rather than string equality. |
| NNG-H8 | Each screen carries only the content and controls its own task needs, so nothing competes for attention with the thing the user came to do (NNG-HEURISTICS, heuristic 8). | For each screen, state its primary task in one sentence drawn from the artifact itself, then classify every element the screen presents as serving that task, serving a secondary task, or serving neither. Flag a screen where elements serving neither outrank the primary control for the user's attention, and flag a primary control that a secondary element outweighs. Prominence is read from what the artifact actually commits to: where it specifies visual weight (size, placement, styling, an above-the-fold note), use that; where it does not, as in an unstyled HTML mockup or a markdown spec, use reading order and repetition, so an unrelated element placed ahead of the primary control, or repeated around it, is what outranking looks like. Do not flag density on its own: a dense screen whose elements all serve its task is not a violation. | A settings page repeats a promotional banner above the fold that pushes the first setting below it, delaying the task without preventing it. | A dashboard's primary action is one small link among twelve equally weighted cards, several of them promotional, so a first-time user cannot locate the thing the screen exists for. | judged | Relevance to the task and relative prominence are readings of the whole screen, not measurable properties of it. |
| NNG-H9-IDENTIFY | Error text in the artifact says in plain language what went wrong and where, specifically enough that the user can tell which of their actions or entries caused it (NNG-HEURISTICS, heuristic 9). | Collect every error, warning, and failure state the artifact defines. Flag a message that only reports that something failed, that surfaces a raw code or exception, or that names a system component instead of the user's action or field. A message naming the field or action and the condition that failed passes. | A form-level message reports that one or more fields are invalid without marking which, on a four-field form where the user can still find it by inspection. | A payment step fails with a generic message and a numeric code, so the user cannot tell whether the card, the address, or the network was at fault, and every retry reproduces the same dead end. | judged | Whether a message is specific enough for its user is a reading of the message against the situation it reports, not a lexical property of the string. |
| NNG-H9-RECOVER | Error text points to a next step the user can actually take, with the control or route for taking it available where the message appears (NNG-HEURISTICS, heuristic 9). | For each error state the artifact defines, check whether it names a recovery action and whether that action is reachable from the error state itself. Flag an error that describes a problem and offers no next step, and flag one whose suggested step is not available where the message appears. | An upload error explains that the file is too large and gives the limit, but offers no direct retry, so the user re-enters the flow from the start. | A session-expired screen states that the session ended and provides neither a sign-in control nor a link back to the page the user was on, ending the task there. | judged | Requires checking whether the suggested step is actionable from where the user is standing, which is a reading of the flow around the message. |
| NNG-H10-FINDABLE | Where the artifact relies on help, documentation, or explanatory content, that content is reachable from the place the user needs it rather than only from a separate destination (NNG-HEURISTICS, heuristic 10). | Identify every step the artifact itself signals as needing explanation: a field with a format rule, a term the interface never defines, a choice with consequences. Check whether help is offered in place as a hint, a tooltip, or a linked explanation. Flag a step that needs explanation and offers none, and flag help that exists only in a global destination the flow never links to. | A field with a non-obvious format states its rule only in a help destination the screen does not link, though the field's own error message states the rule after a failed attempt. | A classification choice that determines the rest of the flow offers no definition of its options anywhere in the artifact, so the user picks blind and the artifact provides no way to correct it later. | judged | Deciding which steps need explanation is a judgment about what this user already knows, not a structural property of the artifact. |
| NNG-H10-TASK-FOCUSED | Help content the artifact includes is written around what the user is trying to do, in concrete steps tied to the interface in front of them, rather than describing the system in the abstract (NNG-HEURISTICS, heuristic 10). | For each help element the artifact contains, check that it names the user's task, gives its steps in the order the interface presents them, and refers to controls by the labels the artifact actually uses. Flag help that describes features rather than tasks, and flag help naming controls the accompanying screen does not have. | A tooltip defines what a field is rather than what to enter in it, beside a field whose label already implies the answer. | An onboarding help panel walks through a menu path that does not exist in the accompanying mockup, so a user following it is hunting for controls the artifact never shows. | judged | Requires comparing help prose against both the task and the mockup, which is a reading of both. |

## De-duplication rules

Three heuristics carry a scripted structural criterion alongside a judged criterion covering the same
heuristic. The pairs are deliberately not proxies for each other, and a finding is reported once:

- **NNG-H3-DEADEND before NNG-H3-EXIT.** A state with no exit at all is the scripted finding. Judge
  NNG-H3-EXIT only on flows that do have an exit, asking whether it is visible, predictable, and
  cheap.
- **NNG-H4-CONTROL-NAMING before NNG-H4-INTERNAL.** A label pair the fixed synonym sets already
  matched is not re-reported as an internal-consistency judgment. NNG-H4-INTERNAL covers meaning
  drift the lists cannot see: icons, domain nouns, repeated patterns.
- **NNG-H6-LABELED before NNG-H6-RECALL.** An unnamed control is the scripted finding. NNG-H6-RECALL
  covers information the user needs and cannot see, not the naming of the control itself.

Each of these rules is a precedence rule, not a licence to leave a defect unreported. All three
assume the scripted lane ran and could read the artifact's structure. `scripts/checks.py` documents
the exact HTML and markdown conventions it recognizes, and against an artifact that uses some other
convention it emits nothing for the criterion that needed them rather than guessing. When that
happens, the judged sibling covers the structural case too, and reports it under its own ID: a state
with no exit at all in a spec whose screens are not `<section id=...>` elements or level-2 headings
is still reported once, as NNG-H3-EXIT. Check what the scripted lane actually returned before
applying a precedence rule; a rule applied against a lane that stayed silent turns a real defect into
a finding nobody owns.

## Boundaries with sibling skills

- **critique-accessibility (`WCAG-*`).** NNG-H6-LABELED overlaps in subject matter with WCAG's
  name-and-label success criteria but not in claim: this criterion asks whether a human user can read
  what a control is, on a static spec, under Nielsen's recognition heuristic. Programmatic name,
  role, and value for assistive technology are `critique-accessibility`'s claim and carry upstream
  WCAG IDs. Neither ID appears in the other skill's registry
  ([S-05 (skills slate)](../../../docs/internal/release-plans/plan_v0.1.0/S-05_skills-slate/spec.md) AC-3).
- **critique-microcopy (`NNG-EM-*`).** The two skills share the `NNG` namespace on purpose and share
  no IDs ([criterion-ids.md](../../../docs/reference/criterion-ids.md), namespace registry).
  NNG-H9-IDENTIFY and NNG-H9-RECOVER evaluate error states as part of a UI spec or mockup: does this
  screen tell the user what happened and what to do next. `critique-microcopy` critiques the strings
  themselves as its artifact. A request that hands over a list of error strings with no interface
  belongs to that skill.

## Severity

Per-criterion severity 2 and 3 anchors are the two columns above.
[`references/severity-anchors.md`](severity-anchors.md) carries the domain-level calibration that the
table cannot: how to rate a defect in a static artifact, the fixed severities the scripted lane
emits, and which of Nielsen's weighing factors this skill does and does not apply.
