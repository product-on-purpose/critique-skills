# WCAG rubric source

Source: WCAG 2.2 (W3C Recommendation), https://www.w3.org/TR/WCAG22/, accessed 2026-07-31.
Operationalization type: open-standard (per `docs/reference/criterion-ids.md`, permanence rule 3, and
ADR 0006). Upstream success-criterion numbers are adopted directly as `WCAG-<n.n.n>`, matching the
criterion-ID grammar in `docs/reference/criterion-ids.md`. Nothing below is a quotation of WCAG's own
criterion text: operationalizations, tests, and anchors are original paraphrase, per ADR 0006's
paraphrase policy; the Operationalization column carries zero quotation marks.

## Scope

WCAG 2.2 Level A and Level AA success criteria (WCAG 2.2 AA conformance requires both), scoped to what
a static HTML page or fragment critique can evaluate from markup and CSS text alone, matching this
skill's artifact claim: HTML pages and fragments, markdown where mappable. `scripts/checks.py` parses
markup and declared CSS; it does not render a page, run a browser, or observe live interaction.

Two exclusions follow from that boundary, both settled in this pass:

- **Criteria requiring live interactive testing are out of scope**, not an oversight: WCAG 2.1.2 No
  Keyboard Trap, WCAG 2.2.1 Timing Adjustable, WCAG 2.5.1 Pointer Gestures, and WCAG 2.5.7 Dragging
  Movements each require observing a running page respond to input over time, which a static-artifact
  critique cannot do. This is a scope decision, not something an ADR is needed for: it follows directly
  from the artifact claim already fixed by `docs/internal/release-plans/plan_v0.1.0/S-05_skills-slate/spec.md`,
  it is not a namespace or cross-skill question, and it is not one of S-05's own Open Questions (OQ-1
  is `critique-clarity`'s PLAIN/WILLIAMS merge, OQ-2 is `critique-microcopy`'s artifact format; neither
  belongs to this skill). Recorded here, where the boundary actually takes effect.
- **WCAG 2.2's former SC 4.1.1 Parsing is correctly absent**, deprecated by WCAG 2.2 itself, not an
  oversight of this registry.

Every finding raised against a criterion below names its element the way `SKILL.md`, "Naming a
location", requires: the element's `id` as a `#id` token, or a double-quoted bounded CSS selector,
or a double-quoted span of its own text. This applies to the judged rows exactly as it does to the
scripted ones. Operational tests below are written in terms of the element they examine precisely
because that element, not the passage around it, is what the finding has to name.

## Lane assignment, revised from the draft pass

The draft registry grouped criteria into "likely scripted" and "likely judged" buckets for orientation
only, per its own note that the grouping was not a lane assignment. Operationalizing each criterion
against `docs/internal/skill-template.md`'s "Scripted lane discipline" (a criterion is scripted only
when a deterministic script can decide it with no judgment call; when in doubt, judged) moved two
criteria out of the draft's "likely scripted" bucket:

- **WCAG-2.4.6 (Headings and Labels)** moves to judged. The draft's scripted-heavy "heading structure"
  expectation is satisfied by WCAG-1.3.1's heading-level-skip check; 2.4.6's own substantive bar is
  whether a heading or label's wording actually describes what follows, which is a comprehension
  judgment, not a fixed pattern.
- **WCAG-3.1.2 (Language of Parts)** moves to judged. Recognizing that a passage is written in a
  different human language than the page's default requires language identification, which is a
  judgment call in the general case; a script can only verify that an already-present `lang` value is
  well-formed (WCAG-3.1.1's test), not detect an untagged foreign-language passage in the first place.

Both moves keep the skill scripted-heavy overall (13 scripted of 22) while following the template's
"when in doubt, judged" rule rather than the draft's provisional grouping. See each row's Lane
rationale below for the rest of the reasoning.

| WCAG-1.4.1 | Color is never the only visual signal that conveys a piece of information, marks a required action, indicates a response, or distinguishes one element from another; a second, non-color signal (text, an icon, an underline, a pattern) always carries the same information. | Flag an element as a violation when it uses color alone, such as red text or a red border, to signal a state (required, error, success, selected) or to distinguish it from surrounding elements, with no accompanying text label, icon, underline, or other non-color signal carrying the same meaning. | A settings page marks the currently active tab only by a colored underline against otherwise identical tab styling, so a color-blind reader can still find the active tab by checking its underlying aria-selected state, but loses the at-a-glance visual cue. | A multi-field form marks every required field by turning its label text red, with no asterisk, no required text, and no other indicator, so a color-blind reader cannot tell which fields are required until they submit the form and encounter an error. | judged | Determining whether color is genuinely the sole carrier of a piece of information, as opposed to one of several redundant signals, requires reading the surrounding content for meaning rather than matching a fixed markup pattern. |
| WCAG-1.4.3 | Text and images of text carry a contrast ratio against their background of at least 4.5 to 1, or at least 3 to 1 when the text is large-scale (at least 18 point, or 14 point and bold), with the standard's own exceptions for incidental text and logotypes. | Resolve each text node's foreground and background color from its declared or inherited CSS values, compute the contrast ratio using the standard's relative-luminance formula, and flag the node as a violation when its ratio falls below 4.5 to 1, or below 3 to 1 when the text qualifies as large-scale. | A page's secondary caption text renders at 4.1 to 1 against its background, just under the 4.5 to 1 minimum, remaining readable for most users but falling short of the threshold. | An entire article's body copy renders at 2.9 to 1 against its background, well under the minimum, making the page's primary reading task hard to complete for low-vision readers across every paragraph. | scripted | The contrast ratio between two resolved colors is computed by a fixed, published formula with no judgment call once the colors themselves are known. |
| WCAG-1.4.4 | A reader can enlarge text up to 200 percent using the browser's own zoom, without losing content, functionality, or the ability to read any part of the page, and the page itself does nothing to block that zoom. | Flag the page as a violation when its viewport meta tag sets user-scalable=no, or sets maximum-scale to a value below 2, either of which disables or caps the browser zoom a reader would otherwise use to enlarge text. | A page's viewport meta tag sets maximum-scale=1.5, so a reader can still enlarge text by half again but cannot reach the doubling the criterion requires, leaving most text legible for most readers and short of the threshold for those who need it most. | A page's viewport meta tag sets user-scalable=no, disabling browser zoom entirely, so a low-vision reader has no way to enlarge any text on the page. | scripted | The viewport meta tag's zoom-blocking attributes are a fixed, literal string pattern to detect; no judgment call is needed once the attribute value is read. |
| WCAG-1.4.10 | Content and functionality remain available, and reading in one direction only, without requiring the reader to scroll in two dimensions, when the page is viewed at a 320 CSS-pixel-wide viewport, the width a reader zoomed to 400 percent on a standard desktop display would see. | Flag an element as a violation when its CSS sets a fixed width in pixels greater than 320 with no responsive override (no max-width property capping it to a percentage or viewport unit, and no media query that removes or shrinks the fixed width below 320 pixels), since such an element forces horizontal scrolling once the viewport narrows to 320 pixels. | One promotional banner mid-page is set to a fixed 400 pixel width with no responsive override, forcing a narrow strip of horizontal scroll past that banner while the rest of the page reflows normally. | The page's entire body wrapper is set to a fixed 960 pixel width with no responsive override, so the whole page requires horizontal scrolling at a 320 pixel viewport, and every line of content is affected. | scripted | A fixed pixel width above the 320 pixel threshold with no responsive override is a mechanical CSS pattern to detect; no judgment call is needed to identify it, even though the check is a documented proxy for the standard's own rendering-based test. |
| WCAG-1.4.11 | The visual boundary of an interactive component, such as a button outline, form-field border, or focus indicator, and the graphical parts of an informational icon or chart, carry a contrast ratio of at least 3 to 1 against the color immediately adjacent to them. | Resolve the declared border, outline, or fill color of an interactive component or informational graphic against its adjacent background color, compute the contrast ratio using the same relative-luminance formula as WCAG-1.4.3, and flag the component as a violation when its ratio falls below 3 to 1. | A single secondary button's border renders at 2.7 to 1 against its background, just under the minimum, while the button's text label itself remains clearly legible. | Every input field's border across an entire form renders at 1.4 to 1 against the page background, close to invisible, so a low-vision reader cannot locate where any field begins or ends without clicking to trigger a focus outline. | scripted | Contrast ratio between two resolved colors is the same fixed formula as WCAG-1.4.3; no judgment call is needed once the colors are known. |
| WCAG-1.4.12 | No content or functionality is lost when a reader overrides a page's line height, paragraph spacing, letter spacing, or word spacing up to the standard's specified minimum values, meaning the page's own layout does not clip or hide text once that extra spacing is applied. | Flag a text-containing element as a violation when its CSS sets both a fixed height or max-height in pixels and overflow: hidden (or overflow: clip), since that combination clips any text that grows taller once a reader's spacing override is applied. | A single pull-quote box sets a fixed max-height with overflow: hidden, so widened spacing clips one sentence at its edge while the surrounding article text reflows normally. | Every card in a product grid sets a fixed height with overflow: hidden around its description text, so widened spacing silently truncates part of the description on every card across the page. | scripted | A fixed height paired with clipped overflow on a text container is a mechanical CSS pattern; no judgment call is needed to identify the combination, even though it is a documented proxy for the standard's own spacing-override test. |
| WCAG-2.4.1 | A reader has a way to skip past a block of content that repeats across pages, such as a navigation menu or a masthead, and reach the page's main content directly, whether through a skip link or through landmark structure assistive technology can navigate by. | Flag the page as a violation when it contains neither a main landmark element (main, or an element carrying role="main") nor a skip link, defined as an anchor element appearing before the first repeated block whose href targets an id that exists later in the same document. | The page provides neither a main landmark nor a skip link, but its markup exposes at most one focusable element ahead of the first heading, so a keyboard reader passes a single control before reaching content and the missing mechanism costs one extra keystroke per page load. | The page provides neither a main landmark nor a skip link, and two or more focusable elements sit ahead of its first heading, so every reader relying on either mechanism must tab through the entire repeated header and navigation block before reaching the page's actual content, on every single page load. | scripted | The presence of a main landmark element or a same-document skip link is a fixed structural pattern; no judgment call is needed to detect either. |
| WCAG-2.4.2 | The page carries a title, exposed through its title element, that describes the page's topic or purpose well enough that a reader scanning a list of open tabs or search results can tell what the page is about. | Flag the page as a violation when its title element is missing, empty after trimming whitespace, or matches a known placeholder default (Untitled, Untitled Document, Document, New Page, Page Title) with no other content. | The page's title element still carries the authoring tool's placeholder default, so the page is announced with something on load and every tab, bookmark, and history entry gets a stable string, but no page of the site can be told apart from any other at a glance. | The page's title element is empty, so nothing is announced when the page loads and every browser tab, bookmark, and search result falls back to the raw URL, with no way to identify the page at all from its title. | scripted | Presence, emptiness, and membership in a small closed set of placeholder strings are all mechanical checks against the title element's text content; no judgment call is needed. |
| WCAG-2.4.3 | When a page can be navigated in sequence, such as by pressing Tab, the order in which interactive components receive focus follows an order that preserves the meaning and operability a sighted reader would expect from the page's visual and logical layout. | Trace the page's focus order (DOM order, adjusted for any explicit tabindex values) against its visual reading order and its logical task order; flag the sequence as a violation when a control receives focus meaningfully out of step with the task it belongs to, such as a submit button reachable before the fields it submits, or a modal's focus landing outside the modal it just opened. | A form's optional save-as-draft link is reachable by Tab one position earlier than the visual layout suggests, a minor surprise a keyboard user recovers from immediately by continuing to tab forward. | A multi-field registration form places its submit button first in focus order, ahead of every field it submits, so a keyboard-only reader who tabs in document order reaches and can trigger submission before ever reaching the fields meant to be filled in first. | judged | Deciding whether a given focus sequence still preserves the page's meaning and task order requires reading the page's layout and purpose, not just comparing tabindex values against DOM order. |
| WCAG-2.4.4 | A link's destination or purpose can be worked out from the link's own text, or from that text together with the sentence, list item, or other context a screen reader exposes alongside it, without requiring the reader to follow the link to find out. | Flag a link as a violation when its accessible name (its text content, or its aria-label or aria-labelledby value when present) trims and lowercases to one of a fixed closed set of generic phrases (click here, here, read more, more, link, this page, learn more) with no aria-label, aria-labelledby, or title attribute supplying additional context. | A single read-more link at the end of one blog post summary has no supplementary aria-label, but it is the only such link on the page and its surrounding paragraph names the article's topic one sentence earlier. | A news homepage's article list uses read-more as the link text for every single headline, with no supplementary aria-label anywhere, so a screen-reader user browsing by links hears an identical, uninformative label repeated for every article on the page. | scripted | Matching a link's accessible name against a fixed, closed vocabulary of generic phrases is a mechanical string comparison; no judgment call is needed to detect the match itself. |
| WCAG-2.4.5 | A reader can locate a given page within its set of pages through more than one mechanism, such as a site search, a sitemap, or a consistent navigation structure, unless the page is one step within a linear process such as a checkout flow. | Inventory every navigation mechanism the page exposes (search form, sitemap link, breadcrumb trail, primary navigation menu, related-links list) and flag the page as a violation when fewer than two of these mechanisms are present and independently capable of leading a reader to this page, unless the page's own content marks it as one step in a linear process. | A content page offers both a primary navigation menu and a breadcrumb trail, but the breadcrumb trail duplicates the same links as the navigation menu rather than offering a genuinely independent path, leaving one true mechanism in practice. | A content page offers no site search, no sitemap, and no breadcrumb trail, relying solely on a reader already knowing to use the primary navigation menu, so a reader who lands on the page directly from a search engine has exactly one way to find any related page. | judged | Deciding whether two present mechanisms are genuinely independent paths, or whether the page is legitimately exempt as one step in a process, requires reading the page's role in the site rather than counting fixed elements. |
| WCAG-2.4.6 | A heading or a form label describes the topic or purpose of the section or control it introduces well enough that a reader scanning headings and labels alone, without reading the surrounding content, can predict what comes next. | Compare each heading and each form label's wording against the content or control it introduces; flag it as a violation when the wording is generic enough (Section, Details, Info, Options) that it fails to distinguish this section or control from any other, or when it misdescribes the content that actually follows it. | One subsection heading reads Details where every sibling heading in the same document names its specific topic, so a reader scanning headings has to open that one section to learn what it covers. | Every step heading in a five-step checkout flow reads only Step followed by its number, with no description of what each step does, so a reader scanning the headings to find, for example, the payment step cannot tell any step apart from the others without opening each one. | judged | Judging whether a heading or label's wording actually captures the topic or purpose of what follows requires reading and comparing meaning, not matching a fixed pattern. |
| WCAG-2.5.3 | When a control carries a visible text label, the same text also appears, in the same order, within the control's programmatic accessible name, so a reader using voice control or a screen reader can refer to the control by the label they can see. | For every control that has both visible text content and a separately-set accessible name (an aria-label or aria-labelledby value that differs from the visible text), normalize both strings by trimming whitespace and lowercasing them, and flag the control as a violation when the normalized visible text does not appear as a substring of the normalized accessible name. | One button in an otherwise consistent toolbar shows the visible label Submit while its accessible name reads Send form now, which does not contain the visible text at all, so a voice-control user can activate every other control in the toolbar by the label they can see and this one control alone refuses. | Every control across a multi-step form carries an accessible name that drops its own visible label text, so a voice-control user finds that naming what is on screen fails everywhere on the page and has no way to learn which spoken phrase any control will answer to. | scripted | Comparing a control's visible text against its accessible name is a mechanical substring check once both strings are extracted; no judgment call is needed. |
| WCAG-3.1.1 | The page's default human language is identified in markup, through the html element's lang attribute, so assistive technology and translation tools select the correct pronunciation, voice, and translation rules for the page's own content. | Flag the page as a violation when its html element has no lang attribute, an empty lang attribute, or a lang value that does not match a well-formed BCP 47 language subtag (a primary subtag of two or three letters, optionally followed by hyphen-separated region or script subtags). | The html element carries no usable lang value, but a wrapper element inside the body declares a well-formed one covering the page's visible content, so assistive technology reading that subtree still selects the right pronunciation and only what sits outside it falls back. | The page's html element carries no usable lang value and no element inside it declares a well-formed one either, so every assistive-technology user relying on it, across the entire page, gets whatever default language their tool falls back to rather than the page's actual language. | scripted | Presence and well-formedness of the lang attribute's value are both mechanical checks against a fixed grammar; no judgment call is needed. |
| WCAG-3.1.2 | Where a passage or phrase within the page is written in a human language different from the page's own default language, that passage carries its own lang attribute identifying its language, so assistive technology switches pronunciation for just that passage. | Read each passage of the artifact's text content and flag a passage as a violation when it is written in a human language different from the page's html lang value and no ancestor element between that passage and the page root carries a lang attribute naming the passage's actual language. | A single foreign-language pull quote midway through an otherwise English article has no lang attribute of its own, so a screen reader mispronounces that one quotation while the rest of the page reads correctly. | An entire bilingual product page interleaves English and Spanish paragraphs throughout, with no lang attribute anywhere marking the Spanish passages, so a screen-reader user hears every Spanish paragraph mispronounced under English pronunciation rules across the whole page. | judged | Recognizing that a passage is written in a language different from the page's own default requires reading and identifying the passage's language, which is a comprehension judgment rather than a fixed markup pattern. |
| WCAG-3.3.1 | When a page detects that something a reader entered is invalid, the specific item in error is identified and the nature of the problem is described to the reader in text, not through color or an icon alone. | For every input flagged as invalid (through an aria-invalid="true" attribute, an error-styling class, or an inline error message present in the markup), check that the associated error text names both which item is wrong and what is wrong with it; flag the pairing as a violation when the error text is present but generic (Error, Invalid, Please fix this field) or when an invalid field carries no associated error text at all. | A single email field's error text reads "Please enter a valid email," which identifies the field and the general problem but not the specific formatting rule the input failed, still leaving most readers able to correct it on the next attempt. | Every invalid field across a ten-field registration form is marked only with a red border and an aria-invalid attribute, with no error text anywhere describing what is wrong with any of them, so a screen-reader user knows something failed but cannot determine which fields or why. | judged | Judging whether error text actually identifies the item and describes the problem, as opposed to restating a generic failure, requires reading the text for meaning rather than matching a fixed pattern. |
| WCAG-3.3.2 | Wherever the page asks a reader to provide input, a label or an instruction accompanies that request, so the reader knows what information is expected before they have to guess from context alone. | For every input, select, and textarea element that is not hidden or disabled, flag it as a violation when it has no programmatically associated label of any kind: no wrapping or for-linked label element, no aria-label, no aria-labelledby, and no title attribute. | A single optional newsletter-frequency dropdown in an otherwise fully labeled preferences form has no associated label, relying on its position next to a heading to convey its purpose. | A checkout form's payment section has no associated label on any of its five fields, so a screen-reader user reaches the section and hears only unlabeled edit boxes with no way to tell which field expects which value. | scripted | Presence of a programmatic label association is a fixed structural pattern to detect across a closed set of markup mechanisms; no judgment call is needed. |
| WCAG-4.1.2 | Every user-interface component exposes its name, its role, and its current value or state programmatically, so assistive technology can determine what the component is, what it currently holds, and report that to the reader; for a custom-built component, the exposed name also has to actually convey what the component does, not merely exist. | For every interactive element built from generic markup rather than a native control (a div or span carrying a click handler or a custom role), check that it carries a role, a programmatically determinable name, and, where applicable, a state; flag it as a violation when any of the three is missing, or when a name is present but is generic enough (button, icon, click here) that it fails to convey the component's actual purpose. | A custom-built dropdown carries the correct role and a name, but its expanded and collapsed states are not exposed through aria-expanded, so a screen-reader user cannot tell whether the dropdown is currently open without activating it to find out. | A custom icon-only delete button built from a div with a click handler carries no role, no accessible name, and no keyboard handler, so a screen-reader user cannot detect the control exists at all, let alone determine that activating it deletes something. | judged | Presence of a role, name, and state is a structural check, but whether a custom control's exposed name actually conveys its purpose, rather than merely existing, is a comprehension judgment the template's own scripted-lane discipline reserves for the judged lane. |

## Count

22 criteria total: 13 scripted lane, 9 judged lane. Above the S-05 spec's >=15 minimum for
`critique-accessibility` (AC-2) and this pipeline's own 15-criterion minimum parameter. All are WCAG
2.2 Level A or AA, matching the skill's WCAG 2.2 AA scope, which by definition includes both levels.
